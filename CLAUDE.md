# GeoTrack — соглашения проекта

## Что это

GeoTrack — сервис AI-аудита сайтов: насколько хорошо бизнес представлен в ответах языковых моделей и поисковых AI-движков. Документы проекта: `docs/product/`.

## Карта репозитория

- `apps/web` — Next.js 15: лендинг, отчёт, админка, API-роуты
- `apps/worker` — Node 22: функции Inngest, Playwright, краулер
- `packages/core` — схемы, контракты, скоринг, адаптеры, учёт стоимости, safe-fetch, переходы статусов
- `packages/config` — веса, пороги, таксономия и персоны запроса, шаблоны находок, профили аудита, справочник локалей, промпты
- `packages/db` — Drizzle-схема, миграции, сиды
- `packages/ui` — общие компоненты отчёта для веба и PDF
- `docs/specs` — спецификации задач, debt.md
- `docs/adr` — архитектурные решения
- `docs/runbooks` — рантбуки
- `docs/product` — документы проекта
- `fixtures/` — HTML-снимки эталонных сайтов, записанные ответы движков, золотые наборы для eval

## Команды

```bash
pnpm install          # установка зависимостей
pnpm dev              # локальная разработка
pnpm test             # тесты (Vitest, без сетевых вызовов)
pnpm test:eval        # eval вероятностного слоя
pnpm db:migrate       # применить миграции
pnpm fixtures:record  # записать живые ответы в фикстуры
pnpm prompts:generate-categories  # сгенерировать канонические наборы промптов
```

- Интерфейсы адаптеров движка (`EngineAdapter`) и модели
- Схема базы данных и миграции

- Границы пакетов: `core` не зависит от `web` и `worker`

- Модуль `packages/core/net/safe-fetch` и фабрика контекстов Playwright (ADR-015)
- Справочник локалей и правило «промпты генерируются на языке локали, а не переводятся» (ADR-019)

## Архитектурные правила v1.2 (план разработки 2026-09-24)

### Внутренний аудит (`is_internal: true`)
- При статусе `delivered` токен отчёта выдаётся, но письмо **не отправляется**
- Открытие отчёта по ссылке аутрича пишет событие `report_opened` с признаком `outreach`
- Флаг `is_internal` устанавливается в форме ручного запуска из админки (по умолчанию включён)

### Категория с лендинга
- Если пользователь выбрал категорию на лендинге или оператор задал её при ручном запуске из админки — шаг `category.detect` **пропускается**, статус `waiting_category` **не наступает**
- Окно выбора категории не имеет крестика: выходы только «Continue» и «None of these»

### Тизерная карточка находки (T-23)
- Тизерный вариант **не содержит** блоков «How to fix», «Корзина» и «Track»
- Размытие закрытых секций лежит поверх **настоящих данных**, не заглушки
- Блок цитаты подписан именем **опрошенного движка**, а не общим лейблом

### Агенты Claude Code (`.claude/agents/`)
- Синтаксис `Agent(name)` в поле `tools:` frontmatter агентного файла — **не изменять**. Он нужен для того, чтобы оркестратор мог вызывать конкретных субагентов по имени (`Agent(code-reviewer)`, `Agent(debugger)`, `Agent(refactorer)`).

### Админка (T-09 / T-09a)
- Вход через тот же Supabase Auth (magic link, Google, Microsoft) — роль определяется по email из белого списка в конфигурации
- Служебный API-ключ используется только в скриптах и CI; пакетные прогоны запускаются из UI
- T-09a зависит от **T-09 и T-25**

## Дизайн: правило 1:1

Страницы фронтенда разрабатывались вручную кодом (не в визуальных редакторах). Эталонные HTML-страницы из `Geotrack_UI.zip` переносятся в проект **без каких-либо изменений дизайна**. Любые отклонения от дизайна (цвета, типографика, отступы, структура блоков) — только по явному письменному согласию продакта. Агент не имеет права самостоятельно «улучшать», «адаптировать» или «упрощать» визуальную часть.

## Запреты

- **Не удалять и не отключать тесты** — нарушение запрещено CI
- **Не ходить в сеть из тестов** — сетевой слой подменяется заглушкой; любая попытка бросает исключение
- **Не выходить в сеть из воркера мимо `safe-fetch` и фабрики Playwright** — ловится линтером по импортам
- **Не проверять тип аудита условиями** — читать параметры из профиля
- **Не менять статус аудита мимо `transition(status, event)`**
- **Не добавлять зависимости без явного упоминания в описании PR** — агенты предлагают несуществующие пакеты
- **Не менять схему данных внутри задачи про интерфейс** — отдельный PR
- **Не подставлять секреты в код и логи**
- **Не менять промпт или модель без прогона eval** — CI проверяет по изменённым путям
- **Не отправлять письмо при `delivered` для `is_internal: true` аудитов**
- **Не запускать `category.detect` когда категория задана с лендинга или из админки**
- **Не переводить промпты между локалями** — генерировать на языке локали (ADR-019)
- **Не класть брендовые и клиентские промпты в кэш** — они персональны; попытка должна бросать исключение в тестах (ADR-021)

## Проверка кода перед PR

Перед созданием нового PR или обновлением существующего PR, если в изменения входят файлы с **кодом продукта** (`.ts`, `.tsx`, `.js`, `.jsx`, `.py` и подобные исходники в каталогах проекта), спроси у пользователя: «Запустить проверку кода агентом orchestrator? (да/нет)». Не создавай и не обновляй PR до явного ответа. При ответе «да» — сначала запусти агента orchestrator, дождись вердикта, затем продолжай с PR.

Проверка **НЕ требуется** и вопрос **НЕ задаётся**, если изменения затрагивают только:
- документацию (`.md`, включая `CLAUDE.md`)
- конфигурацию агентов (`.claude/`)
- файлы настроек и сборки (`package.json`, конфиги, `launch.json`)
- статические ассеты

Если в изменениях есть и код продукта, и служебные файлы — проверка требуется (код важнее).

## Порядок работы

1. Продакт пишет спецификацию в `docs/specs/T-XX.md` по шаблону
2. Агент-исполнитель читает спецификацию и CLAUDE.md, задаёт вопросы до кода
3. Для детерминированного ядра — тесты до кода; для интеграций — сначала фикстура
4. Реализация строго в границах спецификации
5. Агент-ревьюер (отдельная сессия) проверяет дифф против спецификации
6. Продакт принимает по описанию PR и результату на живом сайте

## Темп разработки

Роудмэп задаёт порядок задач, но не фиксирует скорость. Если задачи закрываются быстрее плана — немедленно берём следующую по зависимостям, не ожидая «плановой» недели. Гейты G1/G2/G3 — это контрольные точки качества, а не дедлайны старта следующего блока.

## Текущее состояние

Готово и смёрджено в main: T-01, T-02, T-03, T-04, T-05, T-06, T-07, T-08, T-09, T-10, T-11, T-12, T-13, T-14a, T-14b, T-15, T-16, T-17, T-18, T-19, T-20, T-21, T-22, T-23, T-24, T-25, T-26, T-27, T-28, T-29, T-30, T-31, T-32, T-33, T-34, T-35, T-36, T-37, T-38, T-39, T-40, T-41, T-42, T-43, T-78, T-44, T-00, T-45.

**Независимое код-ревью (2026-10-02), критичные баги #1–#5 — смёрджены (PR #54–#57).**
Вход в админку (цикл редиректов, падение middleware, open redirect), SSRF через
IPv6 в `ip-check`, журнал и снимки drizzle-миграций (+ индексы объявлены в схеме,
скрипт `pnpm db:migrate`), защита `audit-run`. **Следствие для деплоя:** в
production воркер проваливает каждый аудит (`NonRetriableError`), пока нет задачи
на реальную привязку `setAuditRunDeps` к БД и замену заглушек шагов — до неё
реальные платежи включать нельзя. Остальные разделы ревью (баги по областям,
сквозные проблемы качества) — в работе; остатки см. `docs/specs/debt.md`.

**Примечание по T-45.** Paddle как merchant of record (ADR-007) — вебхук
`transaction.completed`, идемпотентность по `event_id`, платный аудит —
новая строка `audits` с `parentAuditId` на тизер (ADR-013), цена — с
сервера (`apps/web/src/lib/paddle-pricing.ts`, не из защищённого
`audit-profiles.v2.json`). Resend добавлен в список внешних провайдеров
(ADR-026). Чекаут — Transactions API + `@paddle/paddle-js` (единственная
новая npm-зависимость; без неё `checkout.url` ничего не открывает — выявлено
реальным прогоном, см. поправку в `docs/specs/T-45.md` и ADR-007); Resend —
сырой `fetch`. Контракт возврата (`type: 'full'`) и вебхук **подтверждены
против реального Paddle sandbox** (2026-10-01); возврат приходит со статусом
`pending_approval`, не мгновенно. Окружение sandbox/prod выбирается по
префиксу ключа (`pdl_sdbx_`/`pdl_live_`, токен Paddle.js — `test_`/`live_`).
Остаются осознанным долгом по решению продакта (`docs/specs/debt.md`): нет
авторизации/рейт-лимита на `/api/checkout`, не защищена двойная оплата одного
тизера, повторный клик «Refund» может дважды обратиться к Paddle, нет
обработки возвратов/чарджбэков, инициированных на стороне Paddle.

**Примечание по T-00.** Scope сужен по решению продакта: только деплой
(Vercel — `apps/web`, Railway/Docker — `apps/worker`) и проверка обязательных
переменных окружения; Sentry/PostHog/Langfuse — отдельная будущая задача.
Для `apps/web` проверка двухуровневая: на этапе сборки
(`apps/web/scripts/check-env.mjs`, обязательна — Vercel не запускает
`next start`, только собирает serverless-функции) и при старте
(`instrumentation.ts`). `apps/worker` получил первый настоящий HTTP-вход
(`server.ts`) — раньше он только экспортировал Inngest-хендлер, никуда не
смонтированный. Корневой `package.json` закрепляет `packageManager`
(`pnpm@9.15.9`) — CI и `Dockerfile` используют ту же версию. Новая
зависимость `tsx` (`apps/worker`, prod) — `node --experimental-strip-types`
не резолвит относительные импорты `.js` → `.ts` в многофайловом графе (см.
`docs/specs/debt.md`). Открытые пункты вне рамок задачи — в `debt.md`
(edge-case'ы `FREE_DAILY_CEILING=0`/нечислового значения в `rate-limit.ts`,
hardening `Dockerfile` под Chromium, сборка Docker-образа не проверялась
вживую).

**Примечание по T-44.** PDF генерируется через отдельный внутренний роут
(`/internal/report-render/[auditId]`, гейт — `AUDIT_SERVICE_KEY`, не
report-токен) и отдельную Playwright-фабрику `createInternalRenderContext`
(ADR-025) — не переиспользует SSRF-хардненную `createAuditContext` из
ADR-015, т.к. цель рендера всегда доверенная, код-сконструированная. Два
пункта остаются в `docs/specs/debt.md`, вне рамок этой задачи: двойная
привилегия `AUDIT_SERVICE_KEY` (создание аудита + чтение любого платного
отчёта) и видимость бакета хранилища PDF — решить до подключения реального
Supabase Storage, иначе это потенциальный обход ADR-006; и отсутствие тестов
на сборку данных PDF (`loadFromDb` — серверный компонент без тестовой
инфраструктуры).

**Примечание по T-29 и T-78.** Техплан версии 1.7 задним числом добавил T-29
зависимость от T-78 (адаптер Claude) — на момент, когда T-29 была сделана,
Claude как движок ещё не существовал в плане. T-29 реализована для трёх
движков; включение Claude в «полный прогон стандартного профиля» — часть
будущей задачи по реальному подключению адаптеров в пайплайн воркера (ни один
из четырёх адаптеров пока не вызывается из `apps/worker` с реальным `apiKey` —
`engines.poll` принимает адаптеры как DI-параметр и протестирован только с
фейковыми).
