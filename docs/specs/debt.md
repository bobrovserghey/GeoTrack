# Технический долг

Сюда агент-исполнитель записывает всё, что сознательно упрощено или отложено внутри задачи. Каждая запись: дата, задача, что упрощено и почему, когда нужно вернуться.

## 2026-09-28, T-78 — ни один адаптер не проверяет причину остановки генерации

Ни `ClaudeAdapter` (`stop_reason`), ни `GeminiAdapter` (`finish_reason`) не проверяют,
была ли генерация модели оборвана по лимиту токенов, — обрезанный ответ сейчас
молча засчитывается как полный. Для `ClaudeAdapter` с `max_tokens: 1024` это не
практический риск: результаты поиска тарифицируются как входные токены,
`cited_text` в цитатах не входит в выход, и реалистичный ответ с одной-двумя
цитатами укладывается в низкие сотни токенов (в фикстуре — 98). Не увеличивать
`MAX_TOKENS` без конкретного случая обрезки — увеличение вдвое только удваивает
потолок стоимости худшего случая, не решая гипотетическую проблему.

Когда возвращаться: если реальные прогоны покажут обрезанные ответы, добавить
проверку `stop_reason === 'max_tokens'` (Claude) / `finish_reason !== 'STOP'`
(Gemini) как общий паттерн для всех адаптеров разом, а не точечно для одного.

## ~~2026-09-28, T-78 — `claude` отсутствует в enum `engine` схемы БД~~ — закрыто 2026-09-30

Закрыто отдельным PR: `packages/db/migrations/0004_claude_engine.sql`
(`ALTER TYPE "public"."engine" ADD VALUE IF NOT EXISTS 'claude'`) + `engineEnum` в
`packages/db/src/schema/pipeline.ts` обновлён. Миграция написана вручную и

0000–0003, когда против реальной БД будет прогнан раннер миграций
(`drizzle-kit migrate` или `migrate()` из `drizzle-orm` — читают файлы из
`migrations/` по `_journal.json`). Единственные реализованные в
`packages/db/package.json` скрипты сегодня — `db:generate` (только пишет
файлы миграций, БД не трогает) и `db:push` (диффит схему напрямую против
живой БД и `migrations/` не читает вовсе); отдельного скрипта `db:migrate`
в репозитории пока нет, хотя CLAUDE.md его упоминает. Если реальное
подключение Supabase пойдёт через `db:push`, файл 0004 не выполнится
как таковой — новое значение enum попадёт в БД диффом схемы, а не
применением этой миграции; это стоит учитывать при выборе способа
первого деплоя.

Отдельно зафиксировано: `drizzle-kit generate` выдал раздутый диф, потому что
у миграций 0002 (`email_gate`) и 0003 (`rate_limits`) нет snapshot-файлов в
`migrations/meta/` — они написаны вручную и добавлены в `_journal.json` без
`drizzle-kit generate`. Из-за этого генератор посчитал разницу от состояния
`0001_snapshot.json`, а не от факта после 0003, и попытался заново добавить
уже существующие колонки. Миграция 0004 написана вручную тем же способом, что
и 0002/0003, с одной строкой. Если кто-то в будущем всё же захочет
использовать `drizzle-kit generate` для следующей миграции — сначала стоит
досоздать `0002_snapshot.json`–`0004_snapshot.json` (или пересобрать снапшоты
целиком), иначе генератор продолжит путать уже применённые вручную изменения
с новыми.

## 2026-09-30, обнаружено при проверке 0004 — `when` записи `idx: 0` в `_journal.json` больше, чем у записей 1–3

`packages/db/migrations/meta/_journal.json`: запись `idx: 0` (`0000_silly_susan_delgado`)
имеет `when: 1789208258931` (~2026-09-12), а записи `idx: 1, 2, 3` — заведомо
меньшие значения (2025-09-15…2025-09-22). Drizzle-мигратор гейтит применение
миграции условием `lastAppliedWhen < migration.when`, где `lastAppliedWhen` —
максимум `created_at` среди уже применённых. На чистой базе это не стреляет
(применяются все миграции разом), но на уже промигрированной базе, где
`idx: 0` применён, любая следующая миграция с `when`, меньшим 1789208258931,
молча не применится. Эта задача (0004) подобрала `when: 1790726400000`, то
есть больше 1789208258931 — сама 0004 корректна. Но `idx: 1, 2, 3`
(уже смёрджены в main) остаются в этой ловушке.

Когда возвращаться: до первого реального подключения Supabase и прогона
миграций — пересчитать `when` во всех записях журнала в строго возрастающем
порядке (или обнулить `idx: 0` до правдоподобной даты), иначе часть истории
миграций 0001–0003 может не примениться против базы, где уже накатили 0000.
