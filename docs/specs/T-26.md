## Детальные правила

### Лимит по домену

- Нормализованный домен = eTLD+1 по public suffix list, punycode → ASCII, нижний регистр (уже реализовано в `normalizeDomain` из `core`).
- Хранить в `audits.domain_normalized`.
- Максимум **1 тизер на `domain_normalized` за скользящие 30 дней**.
- При `is_internal = true` — лимит не применяется.
- Платные аудиты лимитом не затрагиваются (`profile_id != 'teaser'`).

### Лимит по email

- Считать только аудиты, где `email_verified = true` (кликнутый magic link или OAuth).
- Максимум **3 тизера на `email_normalized` за скользящие 30 дней**.
- 4-й запрос (с подтверждённым email) → `429 { reason: 'email_limit' }`.
- При `is_internal = true` — лимит не применяется.

### IP rate limit (мягкий)

- Считать по `X-Forwarded-For` (первый адрес) или `REMOTE_ADDR`.
- Пороги: **5 в час**, **20 в сутки**.
- При превышении: `{ softBlock: true }` — фронтенд показывает Turnstile в видимом режиме, не отказывает.
- Реализация: счётчик в Postgres (`audit_rate_limits`) или Redis; для MVP — Postgres достаточно.

### Дневной потолок сервиса

- Настраивается переменной окружения `FREE_DAILY_CEILING` (число тизеров в сутки).
- При достижении потолка: форма принимает запрос, возвращает `{ reason: 'daily_ceiling', scheduledDate: 'YYYY-MM-DD' }`.
- `scheduledDate` = следующий день UTC после текущего.
- Аудит создаётся сразу с `status = 'queued'` и `scheduled_for = scheduledDate` (новое поле `audits.scheduled_for`); воркер не запускает его до наступления даты.
- При `is_internal = true` — дневной потолок не применяется.

### Проверка одноразовых доменов и MX

- Проверяется **первым шагом воркера**, только когда `audit.emailNormalized != null`.
- Два условия для блокировки (достаточно одного):
  1. Домен email входит в встроенный список `disposable-domains` (статический, ~1000 записей).
  2. DNS не возвращает MX-записи для домена email (через `resolveMx` из `dns/promises`, проксируется через `safe-fetch` или инжектируемый resolver).
- При блокировке: шаг завершается с ошибкой `DISPOSABLE_EMAIL`; оркестратор переводит аудит в `failed`.
- Разрешены: gmail.com, outlook.com, yahoo.com и аналогичные крупные провайдеры (их нет в списке одноразовых, и MX у них есть).

### Флаг `is_internal`

Два пути установки (оба описаны в 9.4 техплана):

1. **Служебный ключ** (`AUDIT_SERVICE_KEY` в заголовке `X-Service-Key`): для CI и скриптов. Живёт только в серверном окружении. При наличии корректного ключа: `is_internal = true`, лимиты по домену/email/IP/очереди пропускаются, но потолок **профиля** применяется.
2. **Подтверждённая сессия из белого списка**: email из `INTERNAL_EMAIL_WHITELIST` (env, запятые-разделитель) + `email_verified = true`. Ввод email из белого списка без клика по magic link или OAuth флаг **не даёт**.

## API

### POST `/api/audits` (существующий, расширяется)

Добавляемая логика (до вставки в БД):

```
1. domainNormalized = normalizeDomain(url)
2. isInternal = validateServiceKey(headers) || isWhitelistedSession(session)
3. result = checkRateLimits({ domainNormalized, emailNormalized, ipAddress, isInternal })
4. if !result.allowed:
   - reason === 'daily_ceiling' → 202 { scheduledDate } (аудит создаётся с scheduled_for)
   - иначе → 429 { reason }
5. При создании сохранить domain_normalized
```

Новые поля ответа при `429`:
```json
{ "error": "rate_limited", "reason": "domain_limit" | "email_limit" | "queue_depth", "retryAfter": "<ISO 8601>" }
```

## Критерии приёмки

1. `POST /api/audits` с тем же доменом дважды в 30 дней → второй ответ `429 { reason: 'domain_limit' }`.
2. `POST /api/audits` с `email_verified = true` четыре раза за 30 дней → четвёртый ответ `429 { reason: 'email_limit' }`.
3. Одноразовый домен email (`mailinator.com`) → первый шаг воркера завершается ошибкой, аудит переходит в `failed`.
4. `X-Service-Key` из `AUDIT_SERVICE_KEY` → `is_internal = true`, лимиты не применяются.
5. Email из белого списка без подтверждения (`email_verified = false`) → `is_internal = false`.
6. При потолке сервиса форма возвращает `202 { scheduledDate }`, не `429`.
7. `audits.locale = 'ro'` принимается без ошибки валидации.
8. Все юнит-тесты `rate-limit.test.ts` и `disposable-email.test.ts` зелёные.
9. Обновлённые тесты `audit-run.test.ts` зелёные (порядок шагов с `disposable-email.check`).
