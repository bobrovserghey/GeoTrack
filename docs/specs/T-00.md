# T-00: Деплой веб и воркера, проверка конфигурации при старте

## Цель

Из техплана (`GEOTRACK_TECH_PLAN_MVP_RU.md`, таблица задач):

> T-00 | Деплой веб и воркера, проверка конфигурации при старте, Sentry, PostHog, Langfuse | зависит от T-01 | Пустой деплой в preview и прод, сервис не стартует с неполной конфигурацией, ошибка видна в Sentry

**Решение продакта (2026-10-01): scope сужен.** Sentry/PostHog/Langfuse —
отдельная будущая задача (техплан сам предлагал этот вариант в CTO review:
«либо T-00 инфраструктура, либо блок T-55–T-60 эксплуатация»). Эта задача —
только:

1. `apps/web` деплоится на Vercel (preview + prod из одного проекта).
2. `apps/worker` деплоится на Railway (Docker).
3. Оба сервиса **фейлят громко при старте**, если в «реальном» окружении
   (не локальная разработка) отсутствует обязательная переменная окружения —
   не деградируют молча, как сегодня.

Последствие сужения: пункт «ошибка видна в Sentry» из оригинального критерия
не реализуется здесь — ошибка старта будет видна в логах деплоя
Vercel/Railway (процесс падает с понятным сообщением), что и так необходимо
для «сервис не стартует». Интеграция с Sentry остаётся в `docs/specs/debt.md`
как отдельная будущая задача.

## Зависимости

- T-01 (монорепо-скаффолд)
- **Обнаружено при подготовке, меняет объём работы:** `apps/worker/src/index.ts`
  сегодня не поднимает HTTP-сервер — только экспортирует Inngest `serve()`
  handler с комментарием «mount at POST /api/inngest in the web app or
  standalone server». Ни один из двух вариантов не реализован нигде в
  репозитории. Это значит, что T-00 не может быть «только конфиги для
  деплоя» — сначала нужен настоящий HTTP-вход для воркера, иначе деплоить
  на Railway (Docker, долгоживущий процесс) нечего.

## Решения

### Критерий «не стартует с неполной конфигурацией» — через `NODE_ENV`, но этого недостаточно для Vercel

Строгая проверка включается когда `NODE_ENV === 'production'`, не по
платформенным переменным (`VERCEL_ENV`/`RAILWAY_ENVIRONMENT`) — так проще и
переносимо между провайдерами. Локальная разработка (`next dev`) остаётся
как сегодня — с демо-данными там, где `DATABASE_URL` не настроен
(`apps/web/src/app/report/[auditId]/page.tsx`, `opengraph-image.tsx`) — это
осознанная фича для локального превью без полной настройки, T-00 её не
трогает.

**Важная находка ревью, меняет план:** изначальная версия решения
полагалась только на `apps/web/src/instrumentation.ts` (хук `register()`,
вызывается при старте Node-процесса). Это работает для `next start`
(самостоятельный процесс — Railway/Docker), но **не работает для Vercel**:
Vercel не запускает `next start` вообще, он собирает вывод `next build` в
serverless-функции, которые инициализируются по требованию. Проверено
эмпирически: `next build` с нулём переменных окружения завершается
**успешно**, ошибка проявляется только при первом вызове функции — ровно
то «подняли с 500 на первом запросе», для предотвращения которого и
существует эта задача. Поэтому проверка теперь двухуровневая:

1. **Время сборки** — `apps/web/scripts/check-env.mjs`, запускается ПЕРЕД
   `next build` через `"build": "node scripts/check-env.mjs && next build"`
   в `package.json`. Чистый JS, не импортирует `src/lib/env.ts` напрямую
   (тот же повод, что и у воркера — см. ниже про `.js`/`.ts`-резолюцию),
   список переменных продублирован — но расхождение копий не оставлено на
   совесть человека: его ловит тест `env-list-sync.test.ts` (см. «Тесты»).
   Сам скрипт при этом подхватывает `.env*`-файлы через
   `process.loadEnvFile()` в том же порядке приоритета, что и Next.js
   (настоящие переменные окружения важнее файла) — иначе гейт отклонял бы
   локальную сборку, которую `next build` собрал бы успешно, потому что
   голый `node` в отличие от Next сам `.env.local` не читает.
   Падает сборка → Vercel показывает деплой как **неудавшийся**, сайт не
   обновляется — то самое «пустой деплой не стартует».
2. **Время запуска** (`instrumentation.ts`, как было) — страхует
   самостоятельный `next start` (Railway/Docker, если веб когда-нибудь
   туда переедет) и общий случай «переменная исчезла между сборкой и
   запуском», которого на Vercel в норме не бывает, но на других
   платформах — бывает.

### Список обязательных переменных — по факту кода, не выдуман

Собран через grep всех `process.env.*` в `apps/web/src`, `apps/worker/src`,
`packages/*/src`. Отмечено, где сегодня уже есть «тихий» фолбэк, который в
проде на самом деле опасен.

**`apps/web`, обязательны при `NODE_ENV=production`:**

| Переменная | Зачем | Сегодняшнее поведение при отсутствии |
|---|---|---|
| `DATABASE_URL` | вся работа с БД | местами тихий demo-fallback (`report/page.tsx`, `opengraph-image.tsx`), местами throw при обращении (`lib/db.ts`) — несогласовано |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase Auth (админка) | throw при первом вызове `createSupabaseBrowserClient()`, не при старте |
| `SUPABASE_SERVICE_ROLE_KEY` | email-роут отправки отчёта | не проверяется вообще до обращения |
| `ADMIN_SECRET` | вход в админку | `getExpectedHash()` тихо возвращает `null` → админка молча недоступна, не ошибка |
| `AUDIT_SERVICE_KEY` | гейт `/internal/report-render` (T-44) | `isValidServiceKey` тихо возвращает `false` на любой запрос |
| `TURNSTILE_SECRET_KEY`, `NEXT_PUBLIC_TURNSTILE_SITE_KEY` | защита от ботов на форме аудита | **опасный фолбэк**: `verifyTurnstile` при отсутствии секрета считает проверку пройденной («dev mode — skip verification») — в проде это означает полное отключение капчи без единого сигнала |
| `NEXT_PUBLIC_APP_URL` | ссылка на отчёт в письме | `?? ''` → письмо уходит со сломанной ссылкой `/report/{id}` без домена |
| `INNGEST_EVENT_KEY` | отправка событий в Inngest Cloud | без ключа SDK работает в dev-режиме подписи — недопустимо в проде |
| `FREE_DAILY_CEILING` | дневной лимит бесплатных аудитов | **опасный фолбэк**: `?? '0'` (`api/audits/route.ts:69`) → `0`, а `packages/core/src/rate-limit.ts:41` трактует `0` как `Infinity`, то есть **лимит выключен совсем**. Без переменной бесплатные аудиты принимаются без ограничения — неограниченные расходы на LLM. (Ровно наоборот к тому, что утверждала первая редакция этой строки: не «лимит 0, приём останавливается», а «лимита нет».) Тот же эффект даёт нечисловое значение: `parseInt('abc')` → `NaN`, сравнение `todayCount >= NaN` всегда ложно — см. `debt.md` про валидацию формы значений |

**`apps/worker`, обязательны при `NODE_ENV=production`:**

| Переменная | Зачем |
|---|---|
| `INNGEST_SIGNING_KEY` | проверка подлинности вебхуков Inngest. Сам `inngest/node`'s `serve()` читает её из `process.env` автоматически и сам откажет на уровне запроса без неё — но тогда ошибка видна только на первом вебхуке, а не при старте контейнера. Валидируем явно, чтобы контейнер падал сразу |

Больше у воркера сегодня нет реальных внешних секретов в runtime-коде — ни
один адаптер движка, ни прямое обращение к БД не вызываются из
`apps/worker` с реальными ключами (см. CLAUDE.md, примечание по T-29/T-78:
`pollEngines` и все степы принимают зависимости через DI, протестированы
только фейками). Список расширится, когда появится реальная проводка —
не выдумываю `GEMINI_API_KEY`/`DATABASE_URL` для воркера сейчас.
Уточнение: `GEMINI_API_KEY` в репозитории всё же читается — в четырёх
eval-скриптах `apps/worker/src/evals/*.eval.ts` (через `process.env['…']`,
каждый сам пропускает прогон с `SKIP`, если ключа нет). Но это скрипты,
запускаемые вручную через `pnpm test:eval`, а не рантайм-код воркера, —
поэтому в обязательный список старта контейнера переменная не входит.

### Воркер: новый HTTP-вход, отдельно от `index.ts`

`apps/worker/src/server.ts` (новый файл) — тонкая обёртка без фреймворка
(Node `http`, минимальная поверхность для Docker-образа):
- `GET /healthz` → `200 ok` (health check Railway, без обращения к БД —
  у воркера пока и нет настоящего подключения к БД, см. выше)
- остальные пути → делегируются Inngest-хендлеру из `index.ts`
  (`handler` уже реализует `GET`/`POST`/`PUT` для `/api/inngest` по
  протоколу Inngest — сервер просто проксирует `req`/`res`)
- перед `listen()` вызывает `validateWorkerEnv()` — при ошибке процесс
  завершается с ненулевым кодом и понятным сообщением в stdout/stderr
  (видно в логах Railway)

`index.ts` не меняется (остаётся чистым экспортом хендлера — полезно для
тестов и для гипотетического будущего варианта «смонтировать в веб-app»).

### Без шага компиляции, но не через `node --experimental-strip-types`

**Обнаружено при реализации, меняет план:** `apps/worker/tsconfig.json`
уже `noEmit: true`, и `pnpm dev`/`test:eval`/`prompts:generate-categories`
везде запускают `.ts` напрямую через `node --experimental-strip-types` —
но этот флаг **никогда не работал** для многофайлового графа в этом
репозитории. (Одиночный скрипт без относительных импортов им запускается
нормально — поэтому `prompts:generate-categories` как раз работает,
см. `debt.md`.) Нативный type-stripping Node требует настоящее расширение
`.ts` в относительных импортах (`import './file.ts'`), а весь монорепозиторий
пишет `.js` по конвенции TypeScript NodeNext/bundler (реальные файлы —
`.ts`) — это несовместимо с голым `node` и подтверждено не версией Node, а
официальной документацией (нет fallback-резолва `.js` → `.ts`). Эмпирически
проверено на уже существующем `apps/worker/src/evals/accuracy-check.eval.ts`
— падает той же ошибкой. Подробности и что ещё это задевает —
`docs/specs/debt.md`.

Для воркера решено точечно: `tsx` как раннер (обычная `dependency`, не
`devDependency` — нужен и в проде), `dev`/`start` воркера —
`tsx watch src/server.ts` / `tsx src/server.ts`. Прочее место с тем же
дефектом — `test:eval` (6 eval-скриптов) — не в рамках T-00,
зафиксировано в `debt.md`.

### Dockerfile — официальный Playwright-образ, не ручной apt-get; `pnpm deploy` вместо копирования всего репо

`apps/worker/Dockerfile`: `FROM node:22` (не `-slim` — меньше риска, что
Playwright-установщику не хватит системных утилит для `apt-get`) +
`playwright install --with-deps chromium` в стадии сборки — не хардкодим
тег `mcr.microsoft.com/playwright:...`, чтобы версия браузера всегда
бралась из фактической версии пакета `playwright` в `package.json`.

Первая стадия копирует весь монорепозиторий (workspace-пакеты
`@geotrack/core`/`@geotrack/db`/`@geotrack/config` резолвятся через
pnpm-симлинки на этапе `pnpm install`, вырезать `apps/worker` в одиночку
нельзя) и запускает `pnpm --filter geotrack-worker deploy --prod
/deploy/worker` — это собственная команда pnpm (не `npm`/`yarn`), которая
кладёт в отдельную папку только нужный для `geotrack-worker` код и его
прод-зависимости, с `workspace:*`-пакетами как настоящими файлами, а не
симлинками. Вторая стадия (`runtime`) копирует только эту папку — в
финальный образ не попадает ни `apps/web`, ни dev-инструменты монорепо.

## Файлы к созданию

1. `apps/web/src/lib/env.ts` — `validateWebEnv()`, чистая функция, список
   обязательных переменных как в таблице выше, бросает `Error` со списком
   ВСЕХ отсутствующих сразу (не одна ошибка на одну переменную — экономит
   циклы «деплой-упало-поправили-ещё раз деплой»).
2. `apps/web/src/instrumentation.ts` — официальный хук Next.js
   (`register()`), вызывает `validateWebEnv()` только при
   `process.env.NEXT_RUNTIME === 'nodejs'` (хук вызывается и для Node, и
   для Edge рантайма — Edge не должен тянуть эту проверку) и
   `NODE_ENV === 'production'`. **Обнаружено при проверке вручную:**
   исключение, брошенное внутри `register()`, само по себе процесс не
   останавливает — `next start` логирует его как
   `unhandledRejection` и продолжает слушать порт, отдавая 500 на каждый
   запрос вместо отказа стартовать (проверено: процесс и порт остаются
   живы). Это ровно то, что должно НЕ происходить по критерию задачи —
   поэтому `register()` сам ловит ошибку и вызывает `process.exit(1)`,
   предварительно напечатав сообщение. Печать — через
   `process.stderr.write(msg, callback)` с выходом из callback'а, а не
   `console.error`: когда stderr — это пайп (так логи собирают
   Vercel/Railway/Docker), записи Node асинхронны, а `process.exit()` их не
   дожидается, поэтому единственная диагностическая строка в логе деплоя
   может обрезаться или потеряться. На случай, если callback не вызовется
   вовсе (stderr закрыт/заполнен), перед записью ставится
   `setTimeout(() => process.exit(1), 1000)` — процесс обязан отказаться
   стартовать, а не остаться жить и отдавать трафик.
3. `apps/worker/src/env.ts` — `validateWorkerEnv()`, та же форма.
4. `apps/worker/src/server.ts` — HTTP-сервер, см. выше.
5. `apps/web/scripts/check-env.mjs` + `apps/web/package.json` (`"build"`) —
   проверка на время сборки, см. выше.
6. `apps/worker/package.json` — `tsx` в `dependencies`, `dev`/`start` на `tsx watch`/`tsx`.
7. `apps/worker/Dockerfile`, `.dockerignore` **в корне репозитория** —
   без него сборка потянула бы в контекст `.claude/` (полный второй чекаут
   репо под `.claude/worktrees/`), локальный `node_modules` (бинарники не
   под linux-архитектуру — сломали бы `tsx` в контейнере) и любые
   `.env`-файлы с настоящими секретами.
8. `railway.json` **в корне репозитория** (не в `apps/worker/`) —
   `healthcheckPath: "/healthz"`, `restartPolicyType: "ON_FAILURE"`.
   Корень — единственное место, согласованное с тем, что внутри указан
   `dockerfilePath: apps/worker/Dockerfile`, а самому Dockerfile нужен
   контекст сборки — корень репо (см. раздел про Dockerfile выше).
9. `apps/web/.env.example`, `apps/worker/.env.example` — документируют
   переменные из таблиц выше (без реальных значений).
10. `docs/runbooks/deploy.md` — ручные шаги, которые делает продакт
    (создание/настройка проектов в уже существующих аккаунтах Vercel/
    Railway/Supabase, Root Directory, переменные окружения, DNS) — **не
    выполняются агентом**: создание аккаунтов/проектов и ввод настоящих
    продакшн-секретов — это действия, которые агент не делает (см. правила
    сессии).
11. Корневой `package.json` — добавлено поле `packageManager`
    (`pnpm@9.15.9+sha512...`), `.github/workflows/ci.yml` — убран
    захардкоженный `version: 12` у `pnpm/action-setup@v4` (теперь читает
    версию из `packageManager`). **Обнаружено при подготовке**:
    `pnpm-lock.yaml` в этом репозитории всегда был в формате `pnpm@9`
    (`lockfileVersion: '9.0'`), а CI при этом явно запрашивал `pnpm@12` — то
    есть несоответствие существовало и до этой задачи, просто было
    незаметно, пока никто не трогал `apps/worker/package.json`. Теперь
    локальная разработка, CI и `corepack enable` внутри `Dockerfile`
    детерминированно используют одну и ту же, проверенно рабочую версию.
12. `.github/workflows/ci.yml` — добавлен шаг `Build web` (`pnpm --filter
    geotrack-web build`) с фиктивными значениями всех 11 переменных,
    заданными прямо в workflow (не секреты — строки вроде `ci`, нужны
    только чтобы пройти `check-env.mjs`). **Обнаружено ревью**: до этой
    задачи CI ни разу не собирал `apps/web` — lint/typecheck/test проходят
    и при реально сломанной сборке. Это не гипотетический риск: именно так
    по ходу этой самой задачи один из промежуточных вариантов
    `instrumentation.ts` (импорт `node:fs` для синхронной записи) сломал
    `next build` целиком (`UnhandledSchemeError`, см. `src/middleware.ts`
    заставляет Next собирать `instrumentation.ts` и для Edge-рантайма) —
    typecheck/lint/test остались бы зелёными, а первый реальный деплой на
    Vercel упал бы. Теперь это ловится в CI.

## Тесты

- `apps/web/src/lib/__tests__/env.test.ts` — у каждой обязательной
  переменной есть тест «отсутствует → в списке ошибок»; все присутствуют →
  не бросает; собирает все отсутствующие в одно сообщение, а не падает на
  первой.
- `apps/worker/src/__tests__/env.test.ts` — то же для `validateWorkerEnv()`.
- `apps/web/src/lib/__tests__/env-list-sync.test.ts` — **защита от расхождения**
  трёх копий списка обязательных переменных, которые не могут импортировать
  друг друга: `src/lib/env.ts` (источник истины, оттуда список теперь
  экспортируется), `scripts/check-env.mjs` (чистый JS под голым `node`) и шаг
  `Build web` в `.github/workflows/ci.yml`. Расхождение иначе молчаливое:
  гейт на сборке перестал бы покрывать переменную, а все остальные тесты
  остались бы зелёными. Проверено, что тест действительно падает при
  расхождении (удалённая переменная в скрипте, опечатка в имени в CI), а не
  проходит вхолостую — есть отдельный кейс на непустоту разбора.
- Явно НЕ тестируется автотестом (не юнит-тестируемо без реального
  процесса/сети): фактический HTTP-сервер (`server.ts`) и фактический
  `next start`. Оба проверены вручную в ходе реализации:
  - воркер (`tsx src/server.ts`): `curl /healthz` → `ok`; `curl /api/inngest`
    → корректный JSON от Inngest SDK с `function_count: 1`;
    `NODE_ENV=production tsx src/server.ts` без `INNGEST_SIGNING_KEY` →
    падает с понятным сообщением, с ключом → поднимается.
  - веб, время сборки (`node scripts/check-env.mjs && next build`): без
    обязательных переменных — `next build` не запускается вообще, exit
    code 1, одна строка со списком всех 11 переменных; со всеми

  - веб, время запуска (`next build && next start`, без флагов, уже с

    Именно на этом шаге обнаружился баг с `process.exit(1)`, описанный выше

  - Сам Docker-образ **не собирался целиком** (`docker build`) — в этой

    артефакт содержит `node_modules/.bin/tsx`, поднимается и отвечает на
