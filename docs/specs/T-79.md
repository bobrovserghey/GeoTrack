# T-79: Подключение пайплайна воркера к БД (deps, отказ шага, конкурентность)

> Номер вне техплана (в нём последний — T-78); создана по итогам независимого
> код-ревью 2026-10-02 (блок A в `docs/specs/debt.md`). Продакт подтверждает номер.

## Цель

Сейчас `audit-run` не работает: `setAuditRunDeps` никогда не вызывается, в
production функция падает `NonRetriableError` (PR #56), а шаги пайплайна — заглушки.
Задача — сделать оркестрацию аудита корректной и устойчивой на **реальной БД**:
после неё воркер честно ведёт аудит по статусам, не залипает при сбое и не
запускается дважды. **Блокер: реальные платежи (T-45) включать только после этой
задачи.**

## Зависимости

- T-02 (схема), T-05 (`transition`, `audit-run-handler`), T-06 (журнал событий),
  T-45 (платный аудит из вебхука отправляет `geotrack/audit.queued`).
- Замена заглушек шагов (`crawlStub`, `enginePollStub`, `brandPromptsStub`) на
  настоящие шаги — **не входит**, отдельные задачи. Эта задача делает «рельсы»,
  по которым они поедут.

## Решения

1. **Реальные `AuditRunDeps` на Drizzle** (`apps/worker/src/deps/`), подключаются
   при старте в `server.ts` через `setAuditRunDeps`. Воркер без `DATABASE_URL`
   падает на старте (`apps/worker/src/env.ts`, T-00).
2. **Чтения внутри `step.run`.** `getAuditIsPaid` и `getAuditEmailNormalized`
   читаются в шаге (результат мемоизируется Inngest), а не в теле функции: иначе при
   реплее значение может измениться и шаги появляются в середине уже
   выполненной истории. Disposable-проверка идёт **после** `wait-email`; ошибка —
   `NonRetriableError` (повтор ничего не изменит). `disposable-check.ts`
   подключается как `checkDisposableEmail`.
3. **Compare-and-set статуса.** `getAuditStatus(id)` читает текущий статус, он —
   исходный для `transition()`; `updateAuditStatus(id, from, to)` делает
   `UPDATE … WHERE id = $1 AND status = $from` и бросает при 0 затронутых строк
   (админ успел сменить статус — воркер не затирает). Таблица переходов
   (`core/audit-status.ts`) **не меняется**.
4. **Путь отказа.** `onFailure` у `auditRun`: `transition(status, 'step_failed',
   { isPaid })` — по ADR-012 платный → `needs_attention`, тизер → `failed`; запись
   `audit_events` (`run.failed` с именем шага и текстом); страница прогресса и
   рантбук `paid-no-report.md` получают видимый терминальный статус. Работает и
   для `timeout_exceeded`/`hard_budget_exceeded`, когда они появятся.
5. **Конкурентность.** `concurrency: { key: 'event.data.auditId', limit: 1 }`.
   Не `idempotency`: он на 24 часа заблокировал бы `admin_restart`. Повтор
   вебхука Paddle уже отсекается в роуте; это защита от повторов клиента Inngest
   и от рестарта из админки поверх идущего прогона.
6. **Журнал событий.** `insertAuditEvent` — `seq = max(seq)+1` внутри транзакции
   (как в `webhooks/paddle` и `refund`), с обработкой коллизии `(audit_id, seq)`.

## Что сознательно не входит

- Настоящие шаги пайплайна и их Drizzle-кэш; адаптеры движков на реальных ключах
  (блок D), реальный краул (блок C) — см. `debt.md`.
- Промпты и eval (блок B). Таймауты шагов и бюджеты — отдельно.
- Изменение таблицы переходов, схемы БД, `Step<I,O>`.

## Файлы

1. `apps/worker/src/deps/audit-run-deps.ts` — реальные deps (Drizzle), фабрика с
   инъекцией `db`.
2. `apps/worker/src/functions/audit-run-handler.ts` — чтения в `step.run`, CAS,
   порядок disposable-проверки.
3. `apps/worker/src/functions/audit-run.ts` — `onFailure`, `concurrency`.
4. `apps/worker/src/server.ts` — вызов `setAuditRunDeps` при старте.
5. `apps/worker/src/env.ts`, `.env.example`, `docs/runbooks/deploy.md` (убрать
   оговорку «каждый аудит красный»), `docs/runbooks/paid-no-report.md`.

## Тесты

- Фейковые deps: реплей функции не меняет набор шагов; email, появившийся между
  проходами, не создаёт новый шаг посреди истории.
- CAS: админ сменил статус между чтением и записью → воркер бросает, статус не
  затёрт.
- Отказ шага: платный → `needs_attention`, тизер → `failed`, событие записано,
  повторный вызов `onFailure` не ломает уже терминальный статус.
- Два одинаковых события `audit.queued` → один прогон (на уровне конфигурации
  функции проверяется `concurrency`).
- Интеграционный прогон на реальной БД (dev-Supabase), вручную, без записи в
  тестовый набор CI (тесты не ходят в сеть).

## Проверка вручную

Платный аудит из sandbox-вебхука → воркер ведёт `queued → running → …`; убитый
шаг переводит аудит в `needs_attention`, кнопка Restart в админке возвращает его
в `running` без дублирующего прогона.
