# T-45: Оплата через Paddle

## Цель

Из техплана:

> T-45 | Оплата через Paddle: вебхуки, создание платного аудита из тизера, письмо подтверждения, возврат из админки, рантбук | зависит от T-43 | Дубль события не создаёт второй аудит, цена берётся с сервера, возврат пишется в журнал

Плюс из `docs/adr/ADR-007-paddle-payments.md`, `ADR-013`, `ADR-014` и
`playbook/integrations.md`: подпись вебхука проверяется всегда; переход в
платный статус — только по вебхуку, не по возврату на страницу успеха;
письмо «оплата получена» уходит сразу после вебхука; возврат — через API
Paddle, с записью в `payments`.

## Зависимости и что уже готово

- T-43 (report-токен) — `generateReportToken` из `@geotrack/core`
  переиспользуется как есть. Обёртку `issueReportToken`
  (`apps/web/src/lib/report-access.ts`) вебхук **не** вызывает: ей нужен
  `db`, а вставка токена должна идти внутри той же транзакции (`tx`), что
  аудит и заказ, иначе откат гонки оставит осиротевший токен. Логика
  идентична — `generateReportToken()` + вставка в `report_tokens`.
- **Схема БД уже содержит нужные таблицы** (`packages/db/src/schema/audits.ts`,
  присутствуют с базовой миграции 0000/0001): `orders` (`paddleEventId`
  unique, `auditId`, `parentAuditId`, `productId`, `amountUsd`, `status`),
  `payments` (`paddleTransactionId` unique, `payload` jsonb). Ни разу не
  использовались в коде. **T-45 не меняет схему** — чистая
  интерфейсно-логическая задача, отдельный PR на схему не нужен.
- **Переход «тизер → платный» — НЕ transition на той же строке** (ADR-013):
  новая строка `audits` с `parentAuditId = id тизера`, `auditType`
  `standard`/`extended`, собственным `profileId`/`profileVersion` из
  `getAuditProfileV2`. Ключ идемпотентности пайплайна не меняется.
- **`admin_refund` уже существует как переход** (`needs_attention → failed`,
  `packages/core/src/audit-status.ts`) — `audit-status.ts` менять не нужно.
  Возврат ограничен аудитами в `needs_attention` (соответствует ADR-014:
  «полный возврат — если отчёт не доставлен за 48 часов или после
  фатального сбоя»). Возврат уже доставленного (`delivered`) аудита — вне
  рамок этой задачи, состояние этого не поддерживает; если понадобится —
  отдельная задача с ADR на новый переход.

## Решения

### Paddle Billing API, не Classic

Classic не выдаётся новым мерчантам. Событие — `transaction.completed`.
Подпись — заголовок `Paddle-Signature: ts=<unix>;h1=<hex-hmac>`,
`HMAC-SHA256(PADDLE_WEBHOOK_SECRET, "${ts}:${rawBody}")`, сравнение
constant-time. Приемлемое окно `ts` — 300 секунд (допуск на сетевые
задержки и ретраи Paddle), что отклонит явно просроченные/переигранные
попытки, не будучи слишком хрупким к реальной доставке.

### Идемпотентность — уникальный индекс `orders.paddle_event_id` + транзакция, не только проверка перед вставкой

`ADR-007`/`ADR-013` говорят «по event_id и по заказу» — используется
**`event_id` из тела вебхука** (не `transaction.id`, как написано в
`playbook/integrations.md` — для `transaction.completed` оба в норме
соответствуют одному платежу 1:1, но `event_id` — официально
рекомендуемый Paddle ключ дедупликации вебхук-доставок, и уже есть колонка
под него). Порядок обработки:
1. `SELECT orders WHERE paddle_event_id = $event_id` — **вне** транзакции,
   это быстрый путь для обычного случая (последовательные ретраи Paddle):
   нашли → 200, ничего не создаём. Гарантию даёт не эта проверка, а
   уникальный индекс в пункте 3.
2. Не нашли → создаём платный аудит + report-токен + `orders` + `payments`
   внутри одной транзакции.
3. Уникальный индекс — страховка от гонки: если два вебхука с одним
   `event_id` одновременно прошли шаг 1 как «не найдено», второй `INSERT`
   упадёт на уникальном индексе, вся его транзакция откатится (включая
   созданный им аудит), обработчик ловит ошибку нарушения уникальности и
   отвечает 200 (победил первый).

### Цена и профиль — по серверной карте `PADDLE_PRICE_ID_* → профиль`, не из `audit-profiles.v2.json`

`audit-profiles.v2.json` — защищённый инвариант (не для цен). Новый модуль
`apps/web/src/lib/paddle-pricing.ts` — карта `{ [priceId: string]:
{ profileId: 'standard'|'extended'; priceUsd: number } }`, читает
`PADDLE_PRICE_ID_STANDARD`/`PADDLE_PRICE_ID_EXTENDED` из окружения,
строится один раз при импорте. `playbook/integrations.md` называет только
`PADDLE_PRICE_ID_STANDARD` — добавляю `PADDLE_PRICE_ID_EXTENDED`, т.к.
ADR-013 явно описывает оба платных тарифа ($79/$199) как реальные,
покупаемые продукты, а не «расширенный только вручную». `priceUsd` — для
записи в `orders.amount_usd` (учёт); серверная карта — источник истины,
значение из тела вебхука (`data.details.totals.total`) используется только
для `payments.amount_usd` (что реально списано), чтобы расхождение было
видно, а не скрыто.

### Чекаут — через Paddle Transactions API с редиректом на `checkout.url`, без клиентского SDK

Paddle Billing поддерживает два способа: оверлей `@paddle/paddle-js` (новая
клиентская зависимость, JS-виджет) или создание транзакции на сервере
(`POST /transactions`) с получением `checkout.url` для обычного редиректа
браузера. Выбран второй — **ноль новых клиентских зависимостей**, кнопка
«Get the full audit — $79» остаётся тем же `<button>` из эталонного
дизайна, только получает `onClick` (fetch → redirect), без изменения
вёрстки (правило 1:1). Новый роут `apps/web/src/app/api/checkout/route.ts`:
принимает `{ teaserAuditId }`, тариф захардкожен как `standard` (на
странице тизера сегодня показана только цена $79 — в эталонном дизайне нет
UI-входа для Extended; серверная/вебхук-часть поддерживает оба тарифа,
кнопки под Extended просто пока негде появиться), создаёт транзакцию у
Paddle с `custom_data: { teaserAuditId }`, возвращает `{ checkoutUrl }`.

### Email — через Resend REST API напрямую (`fetch`), без npm-пакета `resend`

Весь проект избегает тяжёлых SDK у внешних провайдеров (адаптеры движков —
сырой `fetch` с инжектируемым `fetch` для тестов). Resend REST API — один
POST-запрос с Bearer-токеном, пакет не нужен. **Итог: T-45 не добавляет ни
одной новой npm-зависимости.** Новый модуль `apps/web/src/lib/resend.ts`
экспортирует `sendPaymentConfirmationEmail(deps, input)` в том же стиле,
что и адаптеры в `packages/core` — `deps.fetch` инжектируется, тесты не
ходят в сеть. Письмо шлётся **синхронно внутри обработчика вебхука**
(ADR-014: «письмо "оплата получена" уходит сразу после вебхука»), но его
отказ **не должен** откатывать транзакцию или возвращать Paddle ошибку
(аудит уже оплачен и создан — это первично) — обёрнуто в try/catch,
ошибка пишется в `auditEvents` (`eventType: 'payment.email_failed'`) для
видимости в админке, вебхук всё равно отвечает 200.

**Новый провайдер — явное расширение защищённого списка CLAUDE.md**
(«Список внешних провайдеров и ключей»): Resend туда не входил. Решение —
через ADR (`ADR-026-resend-email.md`), сама задача и факт добавления
явно обсуждаются в описании PR — это и есть требуемое согласие продакта
(см. прецедент T-78/ADR-024 для Claude как 4-го движка).

### Возврат из админки — тот же паттерн, что `restart-step`

Новый роут `apps/web/src/app/api/admin/audits/[auditId]/refund/route.ts`:
тот же `isValidSession`-гейт, что `restart-step`. Проверяет
`audit.status === 'needs_attention'` (иначе 409 — `transition()` и так
бросит `TransitionError`, роут ловит и мапит на 409 с понятным телом).
Находит последний `completed`-заказ аудита, дёргает Paddle Refund API
(`POST /adjustments`, `action: 'refund'`, по `paddleTransactionId` из
`payments`), при успехе: `orders.status = 'refunded'`,
`payments.status = 'refunded'`, `auditEvents` (`admin.refund`),
`transition(status, 'admin_refund', {isPaid:true})` → `failed`, письмо
клиенту о возврате (тот же `resend.ts`, другой шаблон, тоже best-effort).
Кнопка `RefundButton.tsx` — копия `RestartButton.tsx` по структуре, с
`window.confirm` перед отправкой (необратимое, реальные деньги — отличие
от перезапуска шага).

### Рантбук «клиент оплатил, отчёта нет»

Назначен на T-45 явно в CTO review (не на неделю 9, как остальные пять).
`docs/runbooks/paid-no-report.md` — по шаблону `deploy.md`/
`golden-set-labeling.md`: как опознать (алерт/фильтр `needs_attention` +
`auditType != teaser` в админке), что сделать сейчас (перезапуск или
возврат через уже существующие кнопки), что чинить потом.

## Что сознательно не входит в рамки

- **Переиспользование паспорта/категории тизера младше 14 дней** при
  создании платного аудита (ADR-013 §3.3) — пайплайн воркера сегодня в
  принципе не исполняется по-настоящему ни для одного реального аудита
  (CLAUDE.md, примечание по T-29/T-78: все степы — DI, фейковые тесты).
  Реализовывать оптимизацию шага, который ещё никогда не запускался в
  проде, преждевременно. `parentAuditId` на новой строке уже есть — ссылка
  для будущей реализации сохранена, сама логика реюза — долг.
- Чекаут-кнопка для Extended ($199) — эталонный дизайн тизера её не
  показывает (см. выше); серверная часть тариф уже поддерживает.
- PostHog-события (`payment_completed` и т.д.) — тот же принцип, что в
  T-00 (observability вне рамок деплой/оплатной механики по решению
  продакта).
- Защита Paddle-аккаунта на реальное одобрение (нужны юридические
  страницы — Terms/Privacy/Refund policy, задача T-51) — бизнес-блокер вне
  кода, код и тесты работают с подписанными тестовыми вебхуками независимо
  от реального статуса аккаунта.
- Автовозврат «если отчёт не доставлен за 48 часов» (ADR-014) — это
  требует отдельного таймера/расписания (вне Inngest-функции, которая
  сегодня не исполняется), пока это ручной шаг по рантбуку.

## Тесты

- `paddle-pricing.test.ts` — известный price-id → правильный профиль/цена; неизвестный → `null`/понятная ошибка (решение по месту в коде).
- `paddle.test.ts` — верная подпись проходит; неверная — отклоняется; просроченный `ts` (> 300с) — отклоняется; `createPaddleTransaction`/`createPaddleRefund` — корректный запрос к фейковому `fetch`, пробрасывают ошибку API как `Error` с понятным сообщением (паттерн адаптеров движков).
- `resend.test.ts` — корректный запрос к фейковому `fetch`; отказ API не бросает исключение наружу (функция сама решает — там, где используется, обёрнуто в try/catch, либо решение принимается на этом шаге).
- Webhook route — дубль `event_id` не создаёт второй аудит (через фейковую БД/тестовый контейнер — решить по месту, вероятно так же, как тестируется `report-access.ts`: минимальный фейковый drizzle-чейн).
- Refund route — отказ при статусе не `needs_attention`; успешный путь пишет `auditEvents`/переводит статус.

## Проверка вручную

Подписанный тестовый вебхук (Paddle sandbox) → curl на `/api/webhooks/paddle` → платный аудит создан, письмо отправлено (или залогирована ошибка отправки), повторная доставка того же события → второй аудит не создаётся. Возврат из админки на тестовом `needs_attention`-аудите → статус `failed`, `orders`/`payments` помечены `refunded`.
