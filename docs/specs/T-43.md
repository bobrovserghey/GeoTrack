# T-43: Веб-отчёт по токену, версия методологии на момент оплаты

## Цель

1. Платный отчёт (`audit.auditType !== 'teaser'`) открывается только по действительному
   report-токену; чужой или отсутствующий токен — отказ.
2. Страницы отчёта отдают заголовки запрета индексации и строгую политику реферера.
3. Отчёт фиксирует и показывает версию методологии, зафиксированную на аудите
   (`audits.methodology_version`), не подставляя незаметно более новую конфигурацию.

## Зависимости

- T-41 (генератор находок) — таблица `findings` уже используется в `report-content.tsx`
- ADR-006 (модель доступа к отчёту) — токен, хэш в базе, сборка сервером при каждом открытии
- ADR-005 (версионирование конфигурации) — `methodology_version` уже пишется в `audits` при создании

## Решения (согласованы с продактом)

- **Скоуп токен-гейта — только платный отчёт.** Тизерный `/report/[auditId]` остаётся
  без токена (уже защищён лимитами ADR-018: домен/email/IP). Новая проверка токена
  применяется только когда `audit.auditType !== 'teaser'`.
- **Версия методологии — параметризованный `getMethodologyByVersion(version)`.**
  Пока существует только `methodology.v1.json`; функция бросает исключение на неизвестной
  версии — так же, как `getAuditProfile` на неизвестном профиле. `score.compute` шаг
  ещё не реализован (нет в `apps/worker`), поэтому пересчёт скора этой задачей не
  затрагивается — только чтение уже сохранённых `scores` и валидация/отображение версии.

## Файл 1: `packages/config/src/index.ts` — `getMethodologyByVersion`

Загрузчик — статический литерал `require` на версию, а не вычисляемый путь:
пакет попадает в webpack-сборку Next.js через `transpilePackages`, и
`require(computedPath)` там превращается в context module, который может не
резолвиться в рантайме. Регистр версий и статические загрузчики защищены от
прототипных ключей (`toString`, `constructor`) через `Object.hasOwn`.

```ts
const METHODOLOGY_LOADERS: Record<string, () => unknown> = {
  '1': () => require('./methodology.v1.json'),
};

export function getMethodologyByVersion(version: string): Methodology {
  if (!Object.hasOwn(METHODOLOGY_LOADERS, version)) {
    throw new Error(
      `Unknown methodology version: "${version}". Known: ${Object.keys(METHODOLOGY_LOADERS).join(', ')}`,
    );
  }
  const raw = METHODOLOGY_LOADERS[version]!();
  return MethodologySchema.parse(raw);
}

export function getMethodology(): Methodology {
  return getMethodologyByVersion('1');
}
```

`getMethodologyByVersion` экспортируется напрямую (`export function`).

## Файл 2: `packages/core/src/report-token.ts`

Тот же криптографический паттерн, что и `progress-token.ts` (32 байта, base64url,
sha256-хэш), отдельный модуль — жизненный цикл и место использования (`report_tokens`,
`tokenType: 'report'`) отличаются от прогресс-токена.

```ts
export function generateReportToken(): { token: string; hash: string } {
  const token = randomBytes(32).toString('base64url');
  return { token, hash: hashReportToken(token) };
}

export function hashReportToken(token: string): string {
  return createHash('sha256').update(token).digest('hex');
}
```

Экспортировать `generateReportToken`, `hashReportToken` из `packages/core/src/index.ts`.

## Файл 3: `apps/web/src/lib/report-access.ts`

Две функции:

- `issueReportToken(db, auditId)` — переиспользуется будущим T-45 (выдаётся при
  создании платного аудита из вебхука оплаты) и ручным прогоном из админки.
- `isValidReportToken(db, auditId, token)` — единая проверка: отсутствующий,
  чужой и истёкший (`expiresAt`) токен одинаково дают `false`, по образцу
  остальных проверок токенов в кодовой базе (`progress`-токен). Хэширует токен
  перед сравнением с БД — сырой токен в SQL-условие не попадает.

```ts
export async function isValidReportToken(
  db: DbClient,
  auditId: string,
  token: string | undefined,
): Promise<boolean> {
  if (!token) return false;
  const rows = await db
    .select({ id: reportTokens.id, expiresAt: reportTokens.expiresAt })
    .from(reportTokens)
    .where(and(
      eq(reportTokens.auditId, auditId),
      eq(reportTokens.tokenType, 'report'),
      eq(reportTokens.tokenHash, hashReportToken(token)),
    ))
    .limit(1);
  const row = rows[0];
  if (!row) return false;
  if (row.expiresAt && new Date() > row.expiresAt) return false;
  return true;
}

export async function issueReportToken(db: DbClient, auditId: string): Promise<string> {
  const { token, hash } = generateReportToken();
  await db.insert(reportTokens).values({ auditId, tokenHash: hash, tokenType: 'report' });
  return token;
}
```

## Файл 4: `apps/web/src/app/report/[auditId]/page.tsx`

- Принимает `token` из `searchParams` (наравне с существующим `pt`); оба поля
  нормализуются к `string | undefined` — Next может передать `string[]` для
  повторяющегося параметра (`?token=a&token=b`), это не должно валить
  `hashReportToken` необработанным исключением (иначе код ответа 500 вместо
  404 сам становится оракулом «токен почти верный»).
- Если `audit.auditType !== 'teaser'`: `isValidReportToken(db, auditId, token)`
  из `lib/report-access.ts`; `false` → `notFound()` (не 403 — не подтверждаем
  существование аудита чужому токену).
- Тизерная ветка (`auditType === 'teaser'`) не меняется.
- **Побочные точки утечки, которые тоже пришлось закрыть:**
  - `opengraph-image.tsx` получает только `params`, без `token` — не может
    проверить токен. Для `auditType !== 'teaser'` отдаёт тот же нейтральный
    фолбэк, что и для несуществующего `auditId` (не показывает баллы платного
    отчёта, не подтверждает его существование).
  - `audit-progress.tsx`: редирект по готовности сохраняет query-string
    (`window.location.search`), иначе платный пользователь терял `?token=` и
    получал `notFound()` на собственном свежесобранном отчёте.
- **Версия методологии в этой задаче не подключается к отображению** — правило
  «правило 1:1» запрещает добавлять в вёрстку то, чего нет в эталонном макете.
  Реальная точка защиты — не рендер (баллы уже посчитаны и лежат в `scores`,
  рендер их не пересчитывает), а будущий шаг `score.compute` и ручной перезапуск
  шага из админки: они обязаны использовать `getMethodologyByVersion(audit.methodologyVersion)`,
  а не последнюю версию конфигурации. Это задача T-45/шага `score.compute`, не T-43;
  здесь эта функция только готовится и тестируется как переиспользуемый примитив.

## Тесты

### `packages/config/src/__tests__/methodology-version.test.ts`
- `getMethodologyByVersion('1')` возвращает валидную конфигурацию
- `getMethodologyByVersion('999')` бросает `/Unknown methodology version/`
- `getMethodology()` эквивалентен `getMethodologyByVersion('1')`

### `packages/core/src/__tests__/report-token.test.ts`
- `generateReportToken()` возвращает разные `token`/`hash` при каждом вызове
- `hashReportToken(token)` детерминирован — совпадает с `hash` из `generateReportToken()`
- токен — валидный base64url, не короче 40 символов (32 байта)
- хэш — 64-символьный hex

### `packages/config/src/__tests__/methodology-version.test.ts`
- `getMethodologyByVersion('999')` бросает `/Unknown methodology version/` —
  включая прототипные ключи (`toString`, `constructor`, `valueOf`,
  `hasOwnProperty`, `__proto__`)

### `apps/web/src/lib/__tests__/report-access.test.ts`
- `isValidReportToken`: отсутствующий токен → `false` без обращения к БД;
  чужой токен → `false`; совпадающий без `expiresAt` → `true`; совпадающий,
  но ещё не истёкший → `true`; истёкший → `false`; лукап идёт по sha256-хэшу,
  сырой токен не попадает в условие запроса (фейковый drizzle-чейн проверяет
  это по значению, а не по описанию)

## Проверка вручную

На дев-окружении с `DATABASE_URL`: создать аудит с `auditType: 'standard'` (через
сид или напрямую), вызвать `issueReportToken`, открыть `/report/[auditId]?token=...`
(ожидается отчёт), затем `/report/[auditId]?token=неверный` и без параметра
(в обоих случаях — 404). Проверить заголовки ответа `X-Robots-Tag` и
`Referrer-Policy` через `curl -I`.

## Что осталось

- Шаг `score.compute` в `apps/worker`, который реально считает и пишет `scores` —
  отдельная задача, не входит в T-43 (в роудмэпе явно не пронумерована; фиксируется
  в `docs/specs/debt.md`).
- Выдача report-токена при создании платного аудита — часть T-45 (Paddle webhook),
  использует `issueReportToken` из этой задачи.
- Отображение «пересчёт в текущей методологии» как отдельного вида — отдельная
  задача после появления `methodology.v2.json`.
