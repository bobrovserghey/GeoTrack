# T-80: Row level security на всех таблицах

> Номер вне техплана (последний — T-79); подтверждает продакт. **Статус: только
> спецификация. Не реализуется, пока не решены остальные баги из ревью** (решение
> продакта 2026-10-03). Правка схемы БД и миграций — защищённый инвариант: реализация
> отдельным PR, согласие на саму миграцию дано 2026-10-03.

## Цель

Закрыть доступ к таблицам через Supabase Data API по публичному ключу. Supabase отдаёт
все таблицы схемы `public` через PostgREST, а ключ `anon` (`NEXT_PUBLIC_SUPABASE_ANON_KEY`)
по замыслу попадает в каждый браузер. Если у таблицы не включён RLS, обладатель этого
ключа может читать и писать её: `audits`, `orders`, `payments`, `users` (email покупателей),
`report_tokens` (хеши токенов), `audit_events` и остальное. В миграциях проекта RLS нет.

**Блокер для публичного запуска и для приёма реальных денег.**

## Почему это безопасно для приложения (проверено по коду 2026-10-03)

- Приложение читает и пишет таблицы **напрямую по `DATABASE_URL`** (Drizzle + postgres-js:
  `apps/web/src/lib/db.ts`, `apps/worker`). Supabase-клиент используется только для Auth:
  `signInWithOtp`, `exchangeCodeForSession`, `signInWithOAuth` — ни одного `.from()`,
  `.rpc()`, `.storage` по таблицам.
- RLS без политик запрещает доступ ролям `anon` и `authenticated` и не затрагивает роль,
  под которой подключается приложение (в Supabase это `postgres` / `postgres.<ref>` с
  атрибутом `BYPASSRLS`, а также владелец таблиц). `FORCE ROW LEVEL SECURITY` **не
  используется**: он применил бы RLS и к владельцу, то есть к самому приложению.
- Auth-таблицы Supabase (`auth.*`) в схеме `auth`, наши миграции их не касаются.

## Решения

1. **`.enableRLS()` на всех 20 таблицах схемы Drizzle** (`packages/db/src/schema/*.ts`):
   `users, audits, audit_events, orders, payments, report_tokens, category_cache,
   tech_checks, offsite_signals, agent_runs, scores, findings, passports, categories,
   competitors, prompts, engine_runs, mentions, sites, pages`. Drizzle-orm 0.36.4 и
   drizzle-kit 0.28.1 это поддерживают; штатный `drizzle-kit generate` даёт ровно 20
   операторов `ALTER TABLE "…" ENABLE ROW LEVEL SECURITY` и снимок с `isRLSEnabled: true`
   (проверено на черновике, патч не сохраняется в репозитории).
2. **Политик нет.** Данные не публичные; доступ с публичным ключом не нужен ни одному
   сценарию. Если когда-нибудь понадобится чтение с клиента — отдельная задача с
   политиками.
3. **Миграция `0005_enable_rls`** с `when` строго больше, чем у 0004 (правило журнала,
   см. `debt.md` «миграции drizzle»), снимок `0005_snapshot.json`, цепочка `prevId`.
4. **Регрессионный тест** `packages/db/src/__tests__/rls.test.ts`: (а) каждая таблица
   схемы (`getTableConfig(t).enableRLS === true`); (б) каждая таблица есть в миграциях как
   `ENABLE ROW LEVEL SECURITY`; (в) в миграциях нет `FORCE ROW LEVEL SECURITY`. Новая
   таблица без RLS должна ронять тест. Замечание из черновика: type-predicate для
   `is(v, PgTable)` в `Object.values(schema)` не проходит `tsc` (в схеме есть `PgEnum`) —
   использовать явное приведение или `Object.values(schema).filter((v) => is(v, PgTable)) as PgTable[]`.
5. **Применение к БД:** боевая и staging — `pnpm db:migrate` (приедет вместе с остальными
   миграциями); dev-база, созданная через `db:push`, получит RLS при следующем
   `db:push`. На существующей БД миграция идемпотентна по смыслу (повторный
   `ENABLE ROW LEVEL SECURITY` на таблице с RLS не ошибка).

## Что проверить перед применением и после

- **До:** какая роль в `DATABASE_URL`. Должна быть `postgres`/`postgres.<ref>` из строки
  подключения Supabase (она обходит RLS). Если подключение идёт под своей, не-владельцем
  и без `BYPASSRLS` ролью, после включения RLS запросы начнут возвращать пустые
  результаты **без ошибки**. Проверка в SQL Editor Supabase:
  `select rolname, rolbypassrls from pg_roles where rolname in ('postgres', current_user);`
- **После:** (а) Supabase → Advisors → Security: нет предупреждений «RLS disabled in
  public»; (б) `select relname, relrowsecurity from pg_class c join pg_namespace n on
  n.oid = c.relnamespace where n.nspname = 'public' and c.relkind = 'r';` — везде `true`;
  (в) запрос с публичным ключом возвращает пусто/отказ:
  `curl "$SUPABASE_URL/rest/v1/audits?select=id" -H "apikey: $ANON_KEY"` → `[]`;
  (г) приложение работает: создание тизера, вебхук оплаты, страница отчёта, вход в админку.

## Что не входит

- Политики и доступ через Data API (не нужны).
- Отключение Data API целиком (вариант защиты второго рубежа: Settings → API → отключить
  Data API; решает продакт, не обязательно при включённом RLS).
- `REVOKE` прав у `anon`/`authenticated` (избыточно при RLS; завязано на Supabase-роли,
  которых нет в обычном Postgres CI).
- Любые другие изменения схемы.
