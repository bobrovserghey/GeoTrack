# ADR-025 — Внутренний рендер PDF: отдельная фабрика Playwright-контекста

**Статус:** Принято
**Дата:** 2026-10-01
**Контекст:** T-44, зависит от T-43

## Контекст

Для PDF воркер печатает страницу отчёта через внутренний маршрут рендера,
без пользовательского токена, лимитов и политики реферера (§9.5 техплана).
Цель печати — всегда наш собственный, доверенный URL (внутренний маршрут
`apps/web`), а не произвольный сайт пользователя.

Существующая фабрика `createAuditContext` (`apps/worker/src/browser/
playwright-factory.ts`, ADR-015) заточена под противоположный случай:
краулинг ПРОИЗВОЛЬНЫХ внешних сайтов. Она резолвит хост через DNS на каждый
запрос и сверяет IP со списком заблокированных приватных диапазонов
(`isBlockedIp` из `safe-fetch`) — это защита от SSRF, когда URL задаёт
недоверенный пользователь. Для печати собственного отчёта эта проверка:
- не нужна — URL формирует код, а не пользователь;
- потенциально вредна — внутренний хост на Railway/Vercel может резолвиться
  в приватный диапазон или не резолвиться вовсе публичным DNS-резолвером,
  и тогда легитимный запрос будет ошибочно заблокирован защитой, рассчитанной
  на противоположную угрозу.

## Решение

Новый, отдельный модуль `apps/worker/src/browser/internal-render-factory.ts`
с функцией `createInternalRenderContext(options: { serviceKey, baseUrl })`:

- вычисляет `allowedOrigin = new URL(options.baseUrl).origin` один раз при
  создании контекста и разрешает запросы к этому origin через новую
  `shouldBlockInternalRequest(url, resourceType, allowedOrigin)`
  (`apps/worker/src/browser/browser-guard.ts`) — **любой другой origin
  блокируется целиком**, без исключений;
- для разрешённого origin не применяет проверки порта/IP-литерала из
  `shouldBlockRequest` (та фабрика рассчитана на недоверенные внешние цели) —
  порт `baseUrl` может быть любым (`:3000` в dev, нестандартный порт
  контейнерной сети), а хост может быть IP-литералом (контейнерная адресация);
  схема (http/https) и блок media/font/websocket остаются обязательными даже
  для разрешённого origin;
- ставит заголовок `x-service-key` на все запросы контекста (передаётся как
  `extraHTTPHeaders` в `browser.newContext(...)`), чтобы внутренний маршрут мог
  отличить печатающего воркера от обычного посетителя.

Целевой URL строится кодом (`{baseUrl}/internal/report-render/{auditId}` в
`apps/worker/src/steps/report-pdf.ts`) — `baseUrl` приходит как DI-поле
`deps.baseUrl` шага `generateReportPdf`, без отдельной переменной окружения;
проводка конкретного значения (например, из `INTERNAL_RENDER_BASE_URL`)
остаётся задачей вызывающего кода (реальное подключение воркера к
инфраструктуре), не этого модуля.

## Причины

- Разделение по уровню доверия к цели — стандартный принцип: SSRF-защита
  (резолв хоста, сверка с `isBlockedIp`, запрет IP-литералов/нестандартных
  портов) нужна там, где цель задаёт недоверенная сторона. Для одного
  заранее известного, код-сконструированного origin эти проверки не защищают
  ни от чего и в первой версии решения ошибочно блокировали типичный dev/
  контейнерный деплой (`localhost:3000`, внутренний IP на нестандартном
  порту) — обнаружено эмпирически на ревью, см. «Поправка» ниже.
- При этом «разрешить этому одному origin всё» — не то же самое, что
  «отключить защиту»: любой запрос на ДРУГОЙ origin блокируется безусловно
  (`shouldBlockInternalRequest` возвращает `blocked: true` на несовпадении
  origin), а не проверяется по внешним правилам. У этого контекста нет
  легитимной причины обращаться куда-либо ещё.
- Два явных модуля вместо одного с режимом-флагом — легче пройти ревью:
  видно по импорту, какой код допускает печать произвольных сайтов,
  а какой — только внутренних.

## Последствия

- `packages/core/net/safe-fetch` и фабрика контекстов Playwright — инвариант
  CLAUDE.md. Это решение не меняет существующую фабрику `createAuditContext`,
  а добавляет вторую, для другого уровня доверия — поэтому фиксируется ADR,
  а не тихим изменением.
- Линтер по импортам (§3.2 техплана: «импорт `playwright` мимо модулей из
  раздела 9.2 ловится линтером») разрешает `playwright` и в новом модуле — он
  так же единственная санкционированная точка выхода в сеть для печати PDF,
  как `createAuditContext` — для краулинга.
- Если в будущем внутренний маршрут рендера станет доступен по адресу,
  который теоретически может быть подменён (например, через пользовательский
  заголовок `Host`), это решение нужно пересмотреть — сейчас предполагается,
  что `baseUrl` задаётся конфигурацией воркера и не выводится из
  пользовательского ввода.

## Поправка 2026-10-01 (в рамках этого же PR, до первого мерджа)

Первая версия решения (см. историю коммитов) переиспользовала
`shouldBlockRequest` целиком, включая его допущение «порт не из {80, 443} —
отказ» и «хост — IP-литерал — отказ». На ревью это было проверено эмпирически
(`http://localhost:3000` → заблокировано, IP-литерал → заблокировано) и
признано дефектом: шаг не мог бы отрендерить PDF ни в локальной разработке,
ни в типичной контейнерной сети. Исправлено явным решением продакта —
вынести сконфигурированный `baseUrl`-origin из-под этих двух проверок
(`shouldBlockInternalRequest`, см. «Решение» выше), оставив полный запрет на
любой другой origin. `docs/specs/debt.md` — соответствующий пункт закрыт.
