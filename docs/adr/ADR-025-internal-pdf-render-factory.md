# ADR-025 — Внутренний рендер PDF: отдельная фабрика Playwright-контекста

**Статус:** Принято
**Дата:** 2026-10-01
**Контекст:** T-44, зависит от T-43

## Контекст

Для PDF воркер печатает страницу отчёта через внутренний маршрут рендера,
без пользовательского токена, лимитов и политики реферера (§9.5 техплана).
Цель печати — всегда наш собственный, доверенный URL (внутренний маршрут
`apps/web`), а не произвольный сайт пользователя.

Существующая фабрика `createAuditContext` (`apps/worker/src/browser/
playwright-factory.ts`, ADR-015) заточена под противоположный случай:
краулинг ПРОИЗВОЛЬНЫХ внешних сайтов. Она резолвит хост через DNS на каждый
запрос и сверяет IP со списком заблокированных приватных диапазонов
(`isBlockedIp` из `safe-fetch`) — это защита от SSRF, когда URL задаёт
недоверенный пользователь. Для печати собственного отчёта эта проверка:
- не нужна — URL формирует код, а не пользователь;
- потенциально вредна — внутренний хост на Railway/Vercel может резолвиться
  в приватный диапазон или не резолвиться вовсе публичным DNS-резолвером,
  и тогда легитимный запрос будет ошибочно заблокирован защитой, рассчитанной
  на противоположную угрозу.

## Решение

Новый, отдельный модуль `apps/worker/src/browser/internal-render-factory.ts`
с функцией `createInternalRenderContext`:

- переиспользует `shouldBlockRequest` из `./browser-guard.js` для базовой
  гигиены (разрешены только http/https, порты 80/443, блокируются
  media/font/websocket) — это ограничение не зависит от доверия к цели
  и остаётся в силе;
- **не делает** резолв хоста и сверку с `isBlockedIp` — целевой URL строится
  кодом (`{baseUrl}/internal/report-render/{auditId}` в
  `apps/worker/src/steps/report-pdf.ts`), а не приходит от пользователя.
  Уточнение по факту кода: отдельной переменной окружения для базового URL
  сейчас нет — он приходит как DI-поле `deps.baseUrl` шага `generateReportPdf`,
  и ни схема, ни origin этого значения нигде не валидируются. То есть
  «URL всегда наш доверенный» — пока незакреплённое допущение о вызывающем
  коде, а не гарантия, которую даёт сам модуль; проводка конфигурации и
  проверка origin ещё не сделаны (см. `docs/specs/debt.md`);
- ставит заголовок `x-service-key` на все запросы контекста (передаётся как
  `extraHTTPHeaders` в `browser.newContext(...)`), чтобы внутренний маршрут мог
  отличить печатающего воркера от обычного посетителя.

## Причины

- Разделение по уровню доверия к цели — стандартный принцип: SSRF-защита
  нужна там, где цель задаёт недоверенная сторона; для собственного URL,
  заданного вызывающим кодом (а не пользователем), она не защищает ни от чего
  и добавляет риск ложного отказа. Оговорка выше остаётся в силе: сегодня это
  допущение о вызывающем коде, а не проверяемое свойство модуля.
- Переиспользование `shouldBlockRequest` (а не полный пропуск всех проверок)
  сохраняет базовую защиту от случайных ошибок (http-редирект на `file://`,
  попытка загрузить шрифт/видео) без specific-to-SSRF логики.
- Два явных модуля вместо одного с режимом-флагом — легче пройти ревью:
  видно по импорту, какой код допускает печать произвольных сайтов,
  а какой — только внутренних.

## Последствия

- `packages/core/net/safe-fetch` и фабрика контекстов Playwright — инвариант
  CLAUDE.md. Это решение не меняет существующую фабрику `createAuditContext`,
  а добавляет вторую, для другого уровня доверия — поэтому фиксируется ADR,
  а не тихим изменением.
- Линтер по импортам (§3.2 техплана: «импорт `playwright` мимо модулей из
  раздела 9.2 ловится линтером») должен разрешить `playwright` и в новом
  модуле — он так же единственная санкционированная точка выхода в сеть
  для печати PDF, как `createAuditContext` — для краулинга.
- Если в будущем внутренний маршрут рендера станет доступен по адресу,
  который теоретически может быть подменён (например, через пользовательский
  заголовок `Host`), это решение нужно пересмотреть — сейчас предполагается,
  что базовый URL внутреннего маршрута задаётся конфигурацией воркера и не
  выводится из пользовательского ввода. Это допущение пока не закреплено
  кодом: значение приходит как `deps.baseUrl` шага `generateReportPdf`, без
  переменной окружения и без валидации схемы/origin.
