# ADR-028 — Row level security на всех таблицах схемы public, без политик

**Статус:** Предложено
**Дата:** 2026-10-03
**Контекст:** задача 2 реестра решений, решение Р-18; спецификация `docs/specs/T-80.md`

Номер 028, а не 027: ADR-027 (DataForSEO) занят открытым PR #67, и повторное
использование номера дало бы коллизию при его мердже.

## Контекст

Схема базы данных и миграции — защищённый инвариант (CLAUDE.md, раздел
«Инварианты»). Решение Р-18 даёт согласие продакта на правку схемы; этот ADR
фиксирует, что именно меняется и почему, как требует порядок работы.

Supabase отдаёт все таблицы схемы `public` через Data API (PostgREST), а ключ
`anon` (`NEXT_PUBLIC_SUPABASE_ANON_KEY`) по замыслу попадает в каждый браузер.
У таблицы без RLS обладатель этого ключа может читать и писать данные. В
миграциях проекта до 0005 RLS нет ни на одной таблице. Под раздачу попадает
всё существенное: `users` (email покупателей), `orders` и `payments`
(платежи), `report_tokens` (хеши токенов доступа к отчётам), `audits` и
`audit_events`.

Это блокер публичного запуска и приёма реальных денег, а не гигиеническое
улучшение: обход модели доступа к отчёту (ADR-006) не требует ничего, кроме
просмотра исходников страницы.

Проверено по репозиторию 2026-10-03:

- приложение читает и пишет таблицы напрямую по `DATABASE_URL` через
  Drizzle и postgres-js. Единственная фабрика — `packages/db/src/client.ts`;
  она вызывается из пяти мест, и все пять берут `DATABASE_URL`:
  `apps/web/src/lib/db.ts` (общий синглтон, через него идёт большинство
  маршрутов), `apps/worker/src/deps/wire.ts`,
  `apps/web/src/app/api/audits/route.ts`,
  `apps/web/src/app/report/[auditId]/page.tsx` и
  `apps/web/src/app/report/[auditId]/opengraph-image.tsx`;
- клиент Supabase используется только для аутентификации:
  `auth.signInWithOtp`, `auth.exchangeCodeForSession`, `auth.signInWithOAuth`.
  Ни одного обращения к таблицам через него нет;
- таблицы Supabase Auth лежат в схеме `auth`, наши миграции её не касаются.

Следовательно, RLS без политик закрывает Data API и не затрагивает ни один
рабочий путь приложения.

## Решение

1. **RLS включается на всех 20 таблицах схемы `public`** через `.enableRLS()`
   в схеме Drizzle. Объявление в схеме, а не только в SQL: иначе `db:push` и
   `drizzle-kit generate` расходятся с базой, и следующая же генерация
   миграции предложит RLS отключить.
2. **Политик нет.** Данные не публичные, и ни одному сценарию продукта не
   нужен доступ с публичным ключом. RLS без политик означает отказ для ролей
   `anon` и `authenticated` и ничего не меняет для роли подключения
   приложения: в Supabase это владелец таблиц с атрибутом `BYPASSRLS`.
   Понадобится чтение с клиента — это отдельная задача с политиками и
   отдельным ADR.
3. **`FORCE ROW LEVEL SECURITY` не используется.** Он применил бы RLS и к
   владельцу таблиц, то есть к самому приложению: каждый запрос начал бы
   возвращать пустой результат. Запрет закреплён тестом.
4. **Миграция только вперёд, отдельным файлом** `0005_enable_rls.sql` — 20
   операторов `ALTER TABLE … ENABLE ROW LEVEL SECURITY`, сгенерированных
   `drizzle-kit generate`, без ручной правки. По смыслу идемпотентна:
   повторное включение RLS на таблице с RLS не ошибка.
5. **Обратной миграции нет.** Отключение RLS вернуло бы таблицы в Data API,
   то есть восстановило бы уязвимость; если понадобится доступ с клиента,
   это делается политикой, а не отключением.

## Последствия

**Что становится лучше.** Публичный ключ Supabase перестаёт давать доступ к
данным. Проверка «новая таблица без RLS» встроена в тесты, поэтому
добавленная позже таблица не окажется открытой молча — CI уронит сборку.
Снимается блокер приёма реальных денег в части доступа к данным (остальные
блокеры — в `docs/specs/debt.md`).

**Что становится сложнее.** Любая будущая работа с данными из браузера
напрямую потребует политики и ADR. Чтение из Supabase Edge Functions или
других клиентов с ключом `anon` перестанет работать — сейчас таких нет.

**Чем это опасно при неверной роли подключения.** Если `DATABASE_URL`
подключается не владельцем таблиц и без `BYPASSRLS`, после применения
миграции запросы начнут возвращать **пустые результаты без ошибки** — самый
неприятный вид отказа, потому что приложение продолжит работать и покажет
пустые отчёты. Поэтому роль проверяется до применения миграции, а не после;
порядок — в `docs/runbooks/deploy.md`, раздел 1, пункт 3.

В обычном случае этого не случится по построению: миграции применяются тем же
`DATABASE_URL`, что использует приложение (`packages/db/drizzle.config.ts` —
единственный источник строки подключения), поэтому роль приложения и есть
владелец созданных таблиц. Проверка нужна против ручной подмены роли в
переменной окружения.

Две тонкости проверки, чтобы её не упростили обратно:

- **Роль берётся из самого соединения, а не из SQL Editor Supabase.** В
  редакторе `current_user` — роль редактора, а не роль из `DATABASE_URL`, и у
  неё `rolbypassrls = true`. Проверка через редактор проходит успешно ровно в
  том случае, от которого должна защищать.
- **Владение проверяется как `pg_has_role(current_user, relowner, 'usage')`, не
  `'member'`.** Postgres решает, обходит ли роль RLS как владелец, по
  унаследованным привилегиям (`has_privs_of_role`), то есть по правилу `USAGE`:
  привилегии владельца доступны сразу, без `SET ROLE`. `MEMBER` означает лишь
  наличие членства, пусть и только через `SET ROLE`. При членстве с `NOINHERIT`
  вариант с `'member'` показал бы успех, а запросы приложения всё равно попали
  бы под RLS — то самое «пусто без ошибки».

**Что остаётся за рамками.** Отключение Data API целиком (вариант защиты
второго рубежа, решает продакт — раздел 7 реестра), `REVOKE` прав у
`anon`/`authenticated` (избыточно при RLS и завязано на роли Supabase,
которых нет в обычном Postgres для CI), политики для любых ролей.
