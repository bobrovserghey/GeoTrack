# ADR-026 — Resend как провайдер транзакционных писем

**Статус:** Принято
**Дата:** 2026-10-01
**Контекст:** T-45, зависит от T-43

## Контекст

`playbook/integrations.md` называет Resend провайдером транзакционных писем
для четырёх задач: T-25 (magic link), T-26 (результат тизера), T-45
(подтверждение оплаты), T-47 (followup через 24 часа). На момент T-45 ни
одна из этих интеграций ещё не реализована — единственная отправка письма в
коде сегодня (`apps/web/src/app/api/audits/[auditId]/email/route.ts`,
T-25/T-26) идёт не через Resend, а через встроенный OTP Supabase Auth
(`supabase.auth.signInWithOtp`) — отдельный, не транзакционный механизм.

T-45 первой из четырёх задач, использующих Resend, реализует письмо
«оплата получена» (ADR-014: «письмо "оплата получена" уходит сразу после
вебхука») и письмо о возврате.

## Решение

1. **Resend подключается через T-45**, а не отдельной предшествующей
   задачей — в техплане для Resend-интеграции как таковой нет отдельного
   номера задачи, она указана внутри T-25/T-26/T-45/T-47. T-45 вводит общий
   модуль (`apps/web/src/lib/resend.ts`) и использует его для двух из
   четырёх типов писем; T-25/T-26/T-47 переиспользуют тот же модуль, когда
   дойдёт очередь.
2. **Сырой `fetch` к REST API Resend, без npm-пакета `resend`.** Тот же
   принцип, что у адаптеров движков в `packages/core` (инжектируемый
   `fetch`, без сетевых вызовов в тестах, без тяжёлого SDK). Resend REST
   API — один POST-запрос с Bearer-токеном, пакет не добавляет ценности,
   которую не даёт сырой fetch.
3. **Идемпотентность через `Idempotency-Key` в самом запросе Resend**
   (`audit_id:email_type`, как описано в `playbook/integrations.md`), а не
   проверкой на своей стороне перед отправкой — повторная доставка Inngest-
   события/вебхука не должна требовать собственной таблицы учёта отправленных
   писем ради одной этой задачи.
4. **Отказ отправки — не блокирует платёж.** Внутри обработчика вебхука
   письмо отправляется best-effort: аудит и запись об оплате уже созданы к
   этому моменту, ошибка отправки пишется в `audit_events`
   (`payment.email_failed`) для видимости в админке, вебхук всё равно
   отвечает 200 — повторная доставка вебхука из-за сбоя письма создала бы
   риск гонки за идемпотентный ключ `event_id`, не решая проблему письма.

## Причины

- Единообразие с уже принятым в проекте стилем интеграции внешних
  HTTP-провайдеров (адаптеры движков, добавленный этой же задачей `paddle.ts`)
  — один паттерн на все внешние REST-интеграции, а не SDK для одних и fetch
  для других.
- Resend API достаточно мал (создание письма — один эндпоинт), чтобы
  обёртка через SDK не экономила код относительно прямого `fetch`.

## Последствия

- **Список внешних провайдеров и ключей** (инвариант CLAUDE.md) пополняется
  Resend — `RESEND_API_KEY`. Явно обсуждается в описании PR этой задачи —
  это и есть требуемое письменное согласие продакта (тот же прецедент, что
  Claude как четвёртый движок, ADR-024).
- `apps/web/src/lib/env.ts` / `apps/web/scripts/check-env.mjs` /
  `.github/workflows/ci.yml` — `RESEND_API_KEY` обязателен при
  `NODE_ENV=production`, синхронизация трёх копий списка проверяется
  `env-list-sync.test.ts` (T-00).
- Домен отправки (SPF/DKIM/DMARC) — настраивается в дашборде Resend при
  реальном подключении, вне кода; см. `docs/runbooks/deploy.md` (будет
  дополнен при подключении Resend к реальному аккаунту).
- T-25/T-26/T-47 при реализации используют `apps/web/src/lib/resend.ts`
  как есть, добавляя свои собственные функции-шаблоны писем по тому же
  паттерну (`sendPaymentConfirmationEmail`/`sendRefundEmail`), не новый
  модуль интеграции.
