# GeoTrack — решения по критическим пунктам технического плана

Дата: 2026-09-11. Версия 1.0. Проект: GEO. Основание: GEOTRACK_TECH_PLAN_CTO_REVIEW_RU.md (v1.0), пункты 1.2, 1.3, 1.4, 1.5, 1.7, 1.8. Формат: шесть решений по шаблону ADR из приложения Г технического плана, нумерация продолжает десять записей недели 0.

## Резюме

Шесть решений закрывают шесть критических пунктов ревью. Все шесть готовы к переносу в `docs/adr/` без правок, для каждого перечислены изменения в техническом плане и в задачах.

**Ключевые предположения**:
- Тарифы из концепции продукта (раздел 6.6): стандартный $79 — три движка, 30 промптов, три конкурента; расширенный $199 — 50 промптов, пять конкурентов, созвон 15 минут.
- Отчёт не хранится как файл и собирается из данных при каждом открытии (план, 4.7) — на этом свойстве построено решение по неудачным платным аудитам.
- Платный аудит покупается только со страницы результата тизера; прямой покупки без тизера в MVP нет.

**Рекомендация**: принять шесть решений как ADR-011 — ADR-016, внести правки из раздела 7 в план до задачи T-01.

**Статус**: решения предложены, ждут утверждения продактом — версия 1.0.

## 1. ADR-011. Канонические промпты категорий и ключ кэша

Закрывает пункт 1.2 ревью.

### 1.1 Контекст

Кэш категорий работает только тогда, когда два сайта одной категории задают движкам одинаковые вопросы. Генератор промптов по паспорту сайта делает тексты уникальными, и кэш промахивается всегда.

### 1.2 Решение

Промпты делятся на два класса с разным происхождением. **Категорийные** промпты — фиксированный набор на категорию, локаль и версию, лежит в `packages/config/prompts/categories/`, генерируется один раз для всех 200 категорий скриптом и правится продактом как данные. **Брендовые** промпты генерируются под конкретный аудит из паспорта и списка конкурентов и никогда не кэшируются. Ключ кэша — идентификаторы, а не текст: `category_id, locale, prompt_set_version, prompt_id, engine_id`.

### 1.3 Состав наборов

Канонический набор категории — 40 промптов в порядке приоритета: discovery 16, problem-led 10, сравнения между пятью ведущими игроками категории 8, альтернативы лидеру 4, локальные 2. Ведущие игроки категории записаны в таксономии, а не берутся с сайта клиента. Брендовые промпты: «что такое {Бренд}», «{Бренд} pricing», «{Бренд} alternatives», «{Бренд} reviews», «{Бренд} vs {Конкурент}» по числу конкурентов профиля.

| Профиль | Категорийных | Брендовых | Итого |
|---|---|---|---|
| Тизер | 10 первых по приоритету | 2 | 12 |
| Стандартный | 26 первых | 4 | 30 |
| Расширенный | 40 | 10 | 50 |

Список конкурентов сайта (T-13) используется для извлечения упоминаний из кэшированных ответов и для брендовых промптов, но не влияет на категорийные.

### 1.4 Причины

- Кэш попадает по идентификатору, изменение текста промпта — это новая версия набора и осознанный промах.
- Продакт правит промпты как файлы, без цикла разработки, как и требует план (3.1).
- Генерация 400 файлов (200 категорий, две локали) стоит единицы долларов и делается один раз в задаче T-14.

### 1.5 Последствия

- Кэш хранит список ответов по ключу; если профилю нужно два повтора, а в кэше один, дозапрашивается один.
- Категория «другое» из окна выбора получает набор ближайшей категории по таксономии или общий набор «SaaS», с пометкой в отчёте.
- Share of voice (A4) считается по кэшированным ответам: извлечение упоминаний клиента запускается на них заново для каждого сайта, это дёшево.
- Первый платный аудит в новой категории стоит полную цену, дальше категория обслуживает тизеры.

## 2. ADR-012. Жизненный цикл аудита

Закрывает пункт 1.3 ревью.

### 2.1 Контекст

Пайплайн дважды ждёт пользователя, и без явной модели состояний оркестратор, интерфейс и админка придумают три разные.

### 2.2 Решение

Состояние живёт в `audits.status`, переходы выполняет одна чистая функция `transition(status, event)` в `core` с табличным описанием разрешённых переходов. Функция входит в детерминированное ядро, тесты пишутся до кода. Оркестратор и API вызывают только её.

| Статус | Что происходит | Выход из статуса |
|---|---|---|
| `queued` | Запись создана, событие отправлено | Оркестратор принял — `running` |
| `running` | Идут шаги | Событие ожидания, завершение, ошибка |
| `waiting_category` | Показано окно выбора | Выбор пользователя; таймаут 10 минут — автовыбор кандидата с наибольшей уверенностью, пометка в отчёте |
| `waiting_email` | Только тизер. Предварительный результат показан, брендовые промпты ждут email | Ввод email — `running`; таймаут 7 дней — `completed` с пометкой «брендовые промпты не выполнялись» |
| `completed` | Все шаги завершены. Для тизера терминальный | Платный — `in_review` |
| `in_review` | Только платный. Ждёт ручной проверки | Одобрение — `delivered`; правила из ADR-014 |
| `delivered` | Токен отчёта активен, письмо отправлено. Терминальный | Перезапуск шага из админки не меняет статус |
| `needs_attention` | Сбой после траты денег, зависание, потолок стоимости платного аудита | Действие админа: перезапуск, доставка частичного, возврат |
| `failed` | Терминальный. Тизер после сбоя или жёсткого потолка; платный после возврата | — |
| `cancelled` | Терминальный, только админ | — |

### 2.3 Правила

- Зависание: `running` без событий 15 минут — платный аудит переходит в `needs_attention` и поднимает алерт, тизер через 20 минут — `failed` с сообщением пользователю.
- Ожидания реализуются через `step.waitForEvent` оркестратора с таймаутом; повторное подтверждение категории или повторный email игнорируются, если аудит не в соответствующем статусе ожидания.
- Выбор категории после автовыбора не принимается: интерфейс показывает, с какой категорией продолжен аудит, и предлагает повторный аудит.
- Каждый переход пишет событие в `audit_events` с монотонным `seq` в рамках аудита. Лента прогресса — производная от переходов и событий шагов, не источник состояния.
- Результат тизера виден с `waiting_email`, отчёт платного аудита — только с `delivered`.

### 2.4 Последствия

- В спецификации T-05 появляются таблица переходов и тесты на каждый запрещённый переход.
- Экран прогресса (T-22) рисует состояние из статуса, а не выводит его из последнего события.
- Админка (T-09) фильтрует по статусу, `needs_attention` — первый экран.

## 3. ADR-013. Профили аудита и переход из тизера в платный

Закрывает пункт 1.4 ревью.

### 3.1 Контекст

Тизер и два тарифа — три разных набора параметров пайплайна. Ключ идемпотентности по `audit_id` не даёт переиспользовать запись тизера для платного прогона, а тарифы нигде не описаны технически.

### 3.2 Решение

**Профиль аудита** — запись в `packages/config/audit-profiles.v1.json`. Аудит хранит `profile_id` и `profile_version`, шаги читают параметры из профиля и не проверяют тип аудита условиями. **Платный аудит — новый `audit_id`** с полем `parent_audit_id`, указывающим на тизер. Ключ идемпотентности не меняется.

| Параметр | Тизер | Стандартный $79 | Расширенный $199 |
|---|---|---|---|
| Страниц краулера | 3 | 50 | 50 |
| Движки | Perplexity | Perplexity, ChatGPT, Gemini | Те же три |
| Промпты и повторы | 12, один | 30, два | 50, два |
| Конкуренты | 0, только упоминания | 3 | 5 |
| Столпы | A предварительно, B, E5 | Все пять | Все пять |

Остальные параметры профиля: число находок (3 шаблонные, 15, 15), ручная проверка (нет, да, да), PDF (нет, да, да), мягкий и жёсткий потолок стоимости ($0,10 и $0,25; $6 и $8; $9 и $12), бюджет машинного времени (90 секунд, 6 минут, 8 минут). Созвон в расширенном тарифе — ссылка Cal.com в письме, не часть пайплайна.

### 3.3 Переход из тизера

- Оплата возможна только со страницы результата тизера; заказ хранит `parent_audit_id` и `product_id`. Соответствие `product_id` — профиль задаётся на сервере.
- Вебхук `paid` создаёт новый аудит с профилем и отправляет событие; идемпотентность по идентификатору события Paddle и по заказу: повторный вебхук не создаёт второй аудит.
- Из тизера переиспользуются паспорт и подтверждённая категория, если тизеру меньше 14 дней; иначе шаги выполняются заново. Краулер выполняется заново всегда: 50 страниц вместо трёх.
- Кэш категорий работает независимо от родства аудитов.
- Лимит «один тизер на домен в 30 дней» на платные аудиты не распространяется; повторный платный аудит одного домена разрешён.

### 3.4 Последствия

- Поле `business_type` из 6.4 плана и профиль — разные измерения: профиль задаёт объём, тип бизнеса — состав критериев.
- В концепции продукта расширенный тариф в разделе 6.1 описан со 100 промптами, в 6.6 — с 50. Принято 50; концепцию поправить.
- Задача T-29 проверяет стандартный профиль; расширенный проверяется на одном сайте в T-48.

## 4. ADR-014. Доставка платного отчёта при сбоях

Закрывает пункт 1.5 ревью.

### 4.1 Контекст

Клиент платит до выполнения аудита. Пайплайн может остановиться по потолку, потерять движок, зависнуть или ждать ручной проверки сутки. Обещание «6 минут» с обязательной ручной проверкой несовместимо.

### 4.2 Решение

Обещание клиенту: **отчёт в течение 24 часов**, обычно в течение часа. Сразу после вебхука уходит письмо «оплата получена, отчёт готовим», страница прогресса доступна по ссылке из письма. Дальше — четыре класса сбоев и правило для каждого.

| Класс | Пример | Правило |
|---|---|---|
| Частичный столп | Движок отдал 429 на всех попытках, SerpAPI исчерпан | Аудит завершается, столп помечен частичным, интервал расширен. Отчёт доставляется. Админ может перезапустить шаг позже — отчёт пересоберётся сам, клиенту уходит письмо «отчёт дополнен». Без возврата |
| Жёсткий потолок стоимости | $8 достигнут на опросе движков | Опрос останавливается, собранные ответы используются, дальше как частичный столп. Статус `needs_attention` для просмотра админом до доставки |
| Фатальный сбой | `score.compute` не собрался, зависание более 15 минут | `needs_attention`, алерт. Админ в течение 24 часов: перезапуск шага или возврат одной кнопкой через API Paddle из админки с автоматическим письмом клиенту |
| Ручная проверка | Продакт недоступен | Окно проверки 24 часа. Если аудит без частичных столпов и без признаков инъекции, по истечении окна отчёт отправляется автоматически. Иначе ждёт |

Правило возврата, фиксируется в условиях: полный возврат, если отчёт не доставлен за 48 часов или после фатального сбоя; частичный столп возврата не даёт.

### 4.3 Причины

- Отчёт собирается из данных, поэтому дополнение шага после доставки — бесплатное свойство архитектуры, а не отдельная функция.
- Автоотправка после 24 часов — единственное отступление от правила «ручная проверка не сокращается» (13.5). Держать оплаченный отчёт дольше суток из-за возможной опечатки вредит больше, чем опечатка; продакт может править после доставки, отчёт пересоберётся.

### 4.4 Последствия

- В T-45 добавляются письмо подтверждения оплаты и кнопка возврата; T-46 зависит от T-47.
- В T-47 добавляется таймер окна проверки и условие автоотправки.
- Обещание «до 6 минут» остаётся внутренним бюджетом (12.1), на лендинге для платного аудита — «в течение 24 часов».
- Рантбук «клиент оплатил, отчёта нет» пишется в T-45, а не на неделе 9.

## 5. ADR-015. Защита исходящих запросов воркера

Закрывает пункт 1.7 ревью.

### 5.1 Контекст

Проверка адреса до запроса не защищает от подмены между резолвом и соединением, а Chromium в Playwright делает запросы сам, мимо проверок в `core`.

### 5.2 Решение

Один модуль `core/net/safe-fetch` и одна фабрика контекстов Playwright, других способов выйти в сеть у воркера нет — это проверяется линтером по импортам.

**Для запросов через undici.** Хост резолвится во все адреса; запрос отклоняется, если хотя бы один адрес в запрещённых диапазонах: IPv4 приватные, петля, 169.254.0.0/16 включая адрес метаданных, 100.64.0.0/10, 0.0.0.0/8, multicast; IPv6 ::1, fc00::/7, fe80::/10 и IPv4-отображённые адреса. Соединение устанавливается на проверенный адрес через собственный `lookup` в агенте undici, SNI и заголовок Host — по имени. Редиректы отключены в клиенте и обрабатываются вручную: до пяти, с полной проверкой на каждом. Схемы http и https, порты 80 и 443, таймаут 15 секунд, тело 2 мегабайта.

**Для Playwright.** Контекст создаётся только фабрикой, которая ставит перехват `route` на все запросы: запрещены схемы кроме http и https, порты кроме 80 и 443, IP-литералы в хосте; имя хоста проверяется тем же резолвером с кэшем на аудит и пропускается только при успехе; ресурсы типов media, font и websocket блокируются. Остаточный риск подмены между резолвом в Node и резолвом Chromium закрывается изоляцией воркера.

**Изоляция воркера.** Приватная сеть Railway для воркера отключена; единственные адресаты внутри инфраструктуры — Postgres и Storage по учётным данным; эндпоинт Inngest на самом воркере принимает только подписанные запросы. Проверка при старте воркера: запрос к адресу метаданных и к приватному диапазону должен завершаться отказом, иначе воркер не поднимается.

### 5.3 Тесты до кода

Резолв в приватный адрес; редирект с публичного адреса на приватный; хост с двумя адресами, один из которых приватный; IPv4-отображённый IPv6; IP-литерал в Playwright; схема `file:` и `data:` в Playwright; порт 8080; шестой редирект; тело больше лимита; попытка импорта undici мимо модуля.

### 5.4 Последствия

- T-08 расширяется на Playwright-фабрику и проверку при старте; оценка задачи растёт с двух-трёх часов до двух задач.
- Тесты B2 с подменой user-agent и сценарии E1 идут через те же два входа, отдельных путей в сеть нет.
- Прокси перед Chromium с собственной фильтрацией — вариант фазы 2, если остаточный риск станет неприемлем.

## 6. ADR-016. Лента прогресса через опрос вместо SSE

Закрывает пункт 1.8 ревью.

### 6.1 Контекст

Долгое SSE-соединение упирается в предел длительности функций Vercel, а тизер живёт минуты плюс ожидание пользователя.

### 6.2 Решение

Лента прогресса — опрос `GET /api/audits/{id}/events?after={seq}` раз в две секунды, пока статус не терминальный. Ответ содержит статус аудита и события с `seq` больше переданного. Клиент хранит последний `seq`, обрыв или перезагрузка страницы не теряют и не дублируют события. Доступ к ленте — по короткоживущему токену прогресса, выданному при создании аудита, не по токену отчёта.

### 6.3 Причины

- Предел длительности функций перестаёт существовать как проблема.
- Тизер на пять минут — 150 запросов к базе, это ничто; лента читается индексом по `audit_id, seq`.
- Для агента-разработчика опрос проще SSE с курсором и переподключением и даёт меньше способов ошибиться.

### 6.4 Последствия

- T-06 переименовывается в «Опрос ленты прогресса», критерий приёмки: перезагрузка и обрыв любой длины восстанавливают ленту без пропусков и дублей; интервал опроса растёт до пяти секунд в статусах ожидания.
- Supabase Realtime остаётся вариантом фазы 2, когда появится кабинет с авторизованными пользователями и RLS на события.
