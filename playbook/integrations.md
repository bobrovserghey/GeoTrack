# GeoTrack — технические интеграции к реализации

Дата: 2026-09-23. Список охватывает все внешние сервисы и библиотеки, которые нужно подключить в ходе разработки MVP и последующих фаз. Порядок — по очерёдности реализации.

---

## Фаза 1 — MVP (задачи T-36 и далее)

### 1. SerpAPI

**Задачи**: T-36 (столп D: D1, D2, D4), уже используется в T-17 (B4 — ранжирование в поиске)

**Зачем**: получение органической поисковой выдачи по брендовым и категорийным запросам. D1 — присутствие домена в топ-10; D2 — share of voice по категорийным запросам; D4 — число ссылающихся доменов. Для тизера — 2 запроса (B4), для платного аудита — 11 запросов.

**Ключи**: `SERP_API_KEY` в `.env`. Лимит расходов выставлять на стороне SerpAPI ($50–100 в месяц на объёмах фазы 1).

**Важно**: недоступность SerpAPI не должна ронять аудит — критерий помечается `measured: false` и исключается из знаменателя. Адаптер возвращает `null` при 429/503, не бросает исключение. Запасной вариант — DataForSEO (идентичный контракт адаптера, переключение через конфигурацию).

---

### 2. axe-core

**Задача**: T-37 (столп E: доступность E1–E3)

**Зачем**: автоматизированная проверка доступности страниц по стандарту WCAG 2.1 AA. Запускается внутри контекста Playwright (фабрика из T-08b). E1 — число критических нарушений; E2 — структурные барьеры (отсутствие меток, alt-текстов); E3 — совместимость со скринридерами.

**Пакет**: `@axe-core/playwright` — для интеграции через уже существующую фабрику контекстов.

**Ключей нет** — библиотека локальная.

**Важно**: JSON-отчёт axe может быть 200–500 КБ. Сохранять в Supabase Storage (приватный бакет артефактов), не в колонку базы данных. Полный отчёт — артефакт; в `ArtifactRef` пишется ссылка.

---

### 3. Resend

**Задачи**: T-25 (magic link для email-гейта), T-26 (письмо результата тизера), T-45 (письмо подтверждения оплаты), T-47 (followup через 24 часа)

**Зачем**: транзакционные письма. Четыре типа: magic link для входа; результат тизера с CTA «купить полный аудит»; подтверждение оплаты; письмо через сутки после доставки отчёта. Шаблоны на английском и румынском.

**Ключи**: `RESEND_API_KEY`. Почтовый домен подтверждается записями DNS (SPF, DKIM, DMARC).

**Важно**:
- Для `is_internal: true` аудитов при статусе `delivered` письмо **не отправляется** (инвариант CLAUDE.md).
- Отправка идемпотентна: повторная доставка события Inngest не отправляет второе письмо. Идемпотентность через `idempotency_key = audit_id + email_type` в API Resend.

---

### 4. Paddle

**Задача**: T-45 (оплата, вебхуки, создание платного аудита из тизера, возврат из админки)

**Зачем**: merchant of record для приёма платежей. Продукт «Standard Audit $79». Поток: пользователь кликает «Buy» → Paddle Checkout → вебхук `transaction.completed` → создание платного аудита → письмо подтверждения.

**Ключи**: `PADDLE_API_KEY`, `PADDLE_WEBHOOK_SECRET`, `PADDLE_PRICE_ID_STANDARD`.

**Важно**:
- Подпись вебхука проверяется всегда, включая тестовое окружение.
- Цена и состав покупки определяются на сервере по `PADDLE_PRICE_ID_STANDARD` — значения из браузера не принимаются.
- Переход в статус `paid` и запуск платного аудита — только по вебхуку, не по возврату пользователя на страницу успеха.
- Повторная доставка вебхука не создаёт второй аудит (идемпотентность по `transaction.id`).
- Возврат — через API Paddle из админки, с записью в `payments` и автоматическим письмом клиенту.
- Запасной вариант до одобрения Paddle: Lemon Squeezy (совместимый контракт вебхука) или ручные счета для первых 5 клиентов.

---

### 5. Cloudflare Turnstile

**Задача**: T-21 (форма ввода URL — смёрджена), активация ключей требуется отдельно

**Зачем**: защита публичной формы аудита от ботов. Виджет встраивается в форму на лендинге. При превышении мягкого IP-лимита (5 тизеров/час) — Turnstile в видимом режиме, а не hard reject.

**Ключи**: `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (публичный, фронтенд), `TURNSTILE_SECRET_KEY` (серверная валидация в API-роуте `/api/audit`).

**Важно**: токен Turnstile проверяется до создания аудита. В тестах подменяется через специальный тестовый sitekey Cloudflare (всегда проходит). Правило «тесты не ходят в сеть» не нарушается при использовании фиктивных ключей.

---

### 6. Langfuse

**Задача**: T-00 (конфигурация при деплое) — должна быть подключена с первого дня, сейчас активна заглушкой

**Зачем**: трассировка вызовов LLM, учёт токенов и стоимости по шагам. Каждый вызов `model.generate` оборачивается в Langfuse span с тегами `audit_id`, `step_name`, `engine`, `profile_id`. Стоимость видна в Langfuse и записывается в базу (`usage` поле `StepResult`).

**Ключи**: `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL` (self-hosted или cloud.langfuse.com).

**Важно**: в тестах Langfuse не инициализируется — SDK принимает `enabled: false` без сетевых вызовов. Ошибка отправки в Langfuse логируется в Sentry, но не роняет шаг.

---

### 7. PostHog

**Задачи**: T-21 (воронка формы), T-26 (открытие отчёта), T-45 (оплата), фич-флаги везде

**Зачем**: продуктовая аналитика воронки и фич-флаги. Ключевые события: `audit_created`, `report_opened`, `report_opened_outreach`, `payment_completed`, `teaser_email_sent`. Фич-флаги: `paid_flow_enabled`, `engine_override`, `locale_ro`.

**Ключи**: `POSTHOG_API_KEY` (сервер), `NEXT_PUBLIC_POSTHOG_KEY` (клиент).

**Важно**: лид считается только при `email_verified: true` — это критерий гейта G1. Внутренние аудиты (`is_internal: true`) исключаются из воронки через свойство события. Фич-флаги — единственный механизм включения платного потока и смены движка: не деплой, не код.

---

### 8. Sentry

**Задача**: T-00 (деплой) — должна быть подключена с первого дня, сейчас активна заглушкой

**Зачем**: мониторинг ошибок в веб-приложении и воркере. Алерт при новом классе ошибок и при переходе аудита в статус `needs_attention`. Критически важно для операционной модели без постоянного человеческого ревью.

**Ключи**: `SENTRY_DSN_WEB` (Next.js), `SENTRY_DSN_WORKER` (Node воркер) — разные проекты в Sentry.

**Важно**: PII (email, домен) не попадают в Sentry breadcrumbs — только `audit_id`. Sentry не блокирует путь пользователя при ошибке отправки.

## Фаза 2 — Подписки и мониторинг (ноябрь 2026 – февраль 2027)

### 9. ClickHouse Cloud

**Задача**: мониторинг — динамика скора и share of voice во времени

**Зачем**: хранение и агрегация временных рядов прогонов аудита. PostgreSQL плохо справляется с OLAP-запросами на больших объёмах `engine_runs`. ClickHouse обрабатывает запрос «как менялся скор за 90 дней» за миллисекунды.

**Ключи**: `CLICKHOUSE_HOST`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`.

**Важно**: таблица `engine_runs` в Postgres уже проектируется с учётом выгрузки в ClickHouse — не менять формат строк без согласованной миграции. Переход не нужен раньше накопления реальных данных (начало фазы 2).

---

### 10. Copilot (Microsoft Bing Chat)

**Задача**: четвёртый адаптер движка

**Зачем**: расширение покрытия AI-поиска. Copilot — значимый источник для B2B-аудиторий. Подключается через Azure OpenAI или Bing Chat API.

**Ключи**: `COPILOT_API_KEY` или `AZURE_OPENAI_KEY` + `AZURE_OPENAI_ENDPOINT`.

**Важно**: контракт `EngineAdapter` зафиксирован как инвариант — новый адаптер реализует его без изменения интерфейса. Включается фич-флагом PostHog, не деплоем.

---

### 11. Temporal Cloud

**Задача**: условная замена Inngest, если расписания и ре-аудиты не укладываются

**Зачем**: надёжная оркестрация длительных воркфлоу с персистентным состоянием. Нужна если мониторинг (еженедельные прогоны) начнёт давать таймауты или retry storms.

**Ключи**: `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE`, `TEMPORAL_TLS_CERT`, `TEMPORAL_TLS_KEY`.

**Важно**: оркестрация изолирована за тонким интерфейсом с первого дня (ADR-012) — именно для этой замены. Шаги аудита не знают про Inngest или Temporal напрямую.

---

### 12. Notion API

**Задача**: экспорт данных мониторинга в базы знаний клиентов

**Зачем**: клиенты хотят видеть динамику скора в своих Notion-воркспейсах. Запускается вручную или по расписанию из кабинета клиента.

**Ключи**: OAuth per-user (не сервисный ключ). Пользователь авторизует интеграцию через OAuth в настройках кабинета.

---

### 13. Linear API

**Задача**: экспорт находок аудита как задач в Linear

**Зачем**: команды разработки хотят получать находки GeoTrack напрямую в Linear как issues с приоритетом и ссылкой на отчёт.

**Ключи**: OAuth per-user (аналогично Notion).

---

## Фаза 3 — Платформа (март–сентябрь 2027)

### 14. Browserbase

**Задача**: агентный слой — автоматизированные сценарии E4–E5 («найти цену», «начать регистрацию»)

**Зачем**: Playwright в воркере не подходит для долгих агентных прогонов (нет изоляции сессий, нет масштабирования). Browserbase — управляемый браузер с API для агентных сценариев.

**Ключи**: `BROWSERBASE_API_KEY`, `BROWSERBASE_PROJECT_ID`.

**Важно**: не заменяет текущий краулер на Playwright. Browserbase включается только для E4–E5 сценариев. Контракт `BrowserContext` остаётся общим для обоих путей.

---

### 15. Cloudflare R2

**Задача**: замена Supabase Storage для артефактов аудита

**Зачем**: при объёме >500 аудитов/месяц Supabase Storage становится дороже R2. R2 также даёт лучший CDN для PDF-ссылок.

**Ключи**: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`.

**Важно**: Storage-интерфейс абстрагирован с первого дня — переключение меняет реализацию без изменения вызывающего кода.

---

### 16. Cal.com

**Задача**: ссылка созвона для расширенного тарифа (Pro/Enterprise)

**Зачем**: в письме доставки расширенного аудита — ссылка для записи на разбор отчёта. Интеграция минимальная: статическая ссылка, не API.

**Ключей нет** — только `CAL_BOOKING_URL` в конфигурации.
